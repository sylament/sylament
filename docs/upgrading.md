# Upgrading

## Requirements

- **`doctrine/orm` ^3.7.** Doctrine's query builder and a to-many mapping's `orderBy` take PHP 8.6's `SortDirection` enum from ORM 3.7 on, and Sylament passes it; the ORM pulls in `symfony/polyfill-php86`, which defines the enum below PHP 8.6. `actions`, `forms`, `panels`, `schemas` and `tables` require it.
- **`symfony/ux-twig-component` and `symfony/ux-live-component` ^3.5.** One rendering change in 3.5 matters to an application that overrides a Sylament template or passes props to one of its components: an explicit `null` prop now replaces the prop's declared default instead of falling back to it (pass the default at the call site, `component.getColor ?? 'primary'`). In 3.5 an `aria-*` attribute set to `false` renders as `aria-x="false"`; use `null` to drop it.

## Composite keys (M7)

Support for [composite keys](composite-keys.md) changes a few things for applications whose entities all have a single identifier:

- **Stricter URLs.** A record key in a URL must be spelled exactly as Sylament writes it. `/admin/articles/05/edit` and `+5` now return 404; before, they opened record 5. So does `5.0` (which opened record 5 on SQLite and MySQL and was a database error on PostgreSQL). For a `uuid` or `ulid` key (`symfony/uid` or ramsey), uppercase, braced and 32-hex spellings now return 404 where PostgreSQL used to resolve them; urn, base58 and base32 spellings return 404 where they were a database error. For a plain DBAL `guid` key on PostgreSQL, only braced and 32-hex spellings return 404: PostgreSQL compares a `uuid` column by value, so an uppercase spelling still opens the record, as before. A custom type whose writer normalises a value — lower-casing it, say — likewise still opens the record under each spelling it folds together, on every platform. On MySQL and SQLite, UUID keys stored as binary now open their record; before, no spelling did.
- **Primary keys are read-only on edit.** Editing an assigned primary key (a slug, a UUID) or an auto-incremented one is refused with *This value cannot be changed.* Before, the key was rewritten or ignored.
- **Taken keys are form errors.** Creating a record with an assigned key runs one extra `SELECT` to check the key is free, and a taken key is a form error instead of a database error.
- **Blank keys are form errors.** A shared-primary-key entity saved with its mapped key association left blank is refused with *This value should not be blank.*, where the create used to fail inside Doctrine.
- **Many-to-many relation queries use `EXISTS`.** Relation managers and attach options over a many-to-many now query with `EXISTS` instead of `IN`. Results are the same. On SQLite, a very large related table can make these queries slower; PostgreSQL and MySQL plan them as before.
- **Removed methods.** `AssociationReader::getIdentifierFieldName()` is gone.
- **Constructor errors are named.** An entity whose constructor requires arguments now fails with a `LogicException` naming the class, instead of PHP's `ArgumentCountError`.
- **Relationship state is re-read after an edit-page save.** `EditRecord::save()` now calls `$schema->loadStateFromRelationships()` after its flush, so a `dehydrated(false)` field inside a relationship repeater item or a relationship group shows what the record holds after each save, rather than what was typed. A page or component that flushes a schema itself should make the same call after its flush, or a relationship repeater item it added is built again on the next save.
- **A relationship field on the inverse side of a many-to-many saves.** A `Select::multiple()` or `CheckboxList` bound to the inverse side now writes the owning side's join rows, where the save reported success and wrote none. Deselecting a member whose owning collection declares `orphanRemoval` is refused with a `LogicException` naming the field, because it would delete the record being saved.
- **Filtered rows count as taken.** The check for a key already in use looks past Doctrine SQL filters. A key held by a soft-deleted or filtered-out row is now a form error instead of a database error.

## Hardening (M7 · 9)

- **Searching a non-text column works on PostgreSQL.** A `searchable()` integer, decimal, boolean, uuid or date column now compares as text there (`LOWER(col || '') LIKE …`), where every search of the table was a database error. String columns are searched exactly as before. `jsonb`, binary and array columns still cannot be searched this way; use `searchable(query:)`.
- **A search that filtered a fetched collection is refused.** A searchable column like `blocks.heading` on a table whose query fetch-joins `blocks` under the alias `blocks` used to narrow each row's collection instead of choosing rows. It now throws a `LogicException` on the first search. Alias the join something the column does not start with, or use `searchable(query:)`. A resource's globally searchable attributes are checked the same way, on the first global search; there the only way out is to alias the join differently, since an attribute has no `searchable(query:)`.
- **`$recordRouteKeyName` is checked.** Naming an association, a name the record class does not map as a field, or one field of a several-field identifier now throws a `LogicException` on first use (the first row it keys or URL it binds), where it failed later with a database or printing error, or, for one field of several, resolved a record by that field alone and failed once two records shared its value.
- **Replicate names its refusals.** A `ReplicateAction` whose copy would carry a key another record already holds is refused with a `LogicException` naming the fix (or, with a modal, *This value is already used.*), where Doctrine raised `EntityIdentityCollisionException` or a unique violation. A single string key a `prePersist` hook leaves blank is refused by name where Doctrine raised `ORMInvalidArgumentException`.
- **Second-level cache.** The by-key bulk delete evicts the cached entities of the class it deletes from. The by-key bulk dissociate evicts the cached entities of the class it updates and the owner association's cached collections.
- **Int keys.** `IdentifierConstraint::in()`, `notIn()`, `inColumns()`, `chunk()`, `batch()`, `equals()` and `notEquals()` accept int keys.

## Extensibility (M7 · 10)

- **A `query()` table that overrides `getTableRecordKey()` is refused.** On a `query()` table every read back — finding a row, a selection, select-all, reordering, a bulk delete — decodes the key Sylament mints, so an override answering another key found nothing, and select-all with one row unticked deleted the unticked row too. Such an override now throws a `LogicException` naming both keys on the first render. Return the key `RecordKey::of()` returns, or list the rows through `records()`. A `records()` table, and a row Sylament cannot key (an array, a DTO), are unaffected.
- **A taken key is shown under every key field.** *This value is already used.* now appears under each key field of the form that is not an association — the host and the path of a key made of two strings — where it appeared under the first only. A key made only of associations, and a translation keyed by its article and a locale, show it where they did.
- **A value a form hook adds and no field maps is refused.** A `mutateFormDataBeforeCreate()`, `mutateFormDataBeforeSave()` or action `mutateDataUsing()` that adds a key no field of the form maps now throws a `LogicException`, where the value was dropped in silence: `The <owner> added [<paths>] in <hook>, but no component of its <form or schema> maps those paths, so the default write would drop them. Map each with a component — a Hidden one for a value the user should not type, with required(false) where the record would otherwise require it — or <way out>.` The owner is the resource page, the action or the select's option action; the way out is setting it on the record in `makeRecord()` or `handleRecordCreation()` (create page) or `handleRecordUpdate()` (edit page), or taking the write over with `using()` (an action) or `createOptionUsing()` / `updateOptionUsing()` (a select). Overwriting a field's value is unchanged, and a key the browser sent is never refused.
- **`Select`'s create- and edit-option actions keep their data.** A `mutateDataUsing()` on them was discarded; it now reaches the record, and a key it adds that no field maps is refused as above.
- **Records whose constructor takes arguments.** The resource create page builds its record in a new `makeRecord(array $data): object`; override it to call the constructor. With no parent resource, a closure taking `$record` while the form is mapped now receives the new record instead of `null`, as it already did under a parent. A field mapped onto a property with no setter — a `readonly` key the constructor sets — used to fail with Symfony's `NoSuchPropertyException`; it is now left alone when it already holds the value the form writes, and refused with a `LogicException` naming the field when it does not. "The same value" is strict for a bool, for two strings (`'7'` over a held `'007'` is another value) and for an entity mapped with Doctrine attributes (the same instance); a blank field matches only a held `null` or `''`; a numeric string matches its number (`'5'` over a held `5`); two arrays match element by element under the same rule; and two dates or value objects of one class match when they compare equal.
- **The automatic key checks can be switched off.** `Schema::validateRecordKey(false)` skips the taken-key and blank-key checks, leaving them to you and the database. A changed key on edit is still refused. A key field over a non-nullable property is still required by the field itself, so left blank it is still *This value should not be blank.* under the field. A key field the form maps that is not required — it declares `required(false)`, or its property is nullable — is not refused under it, and what happens then depends on what the blank reaches the record as. Whitespace reaches it as a string and fails the save with the existing error naming the class, which adds: *The schema switches the key rules off with validateRecordKey(false), so a key field it maps is not refused while blank; switch them back on to have the blank field refused under it.* An empty field becomes `null`: over a nullable property Doctrine refuses it inside `persist()` with its own `EntityMissingAssignedId` (*Entity of type … is missing an assigned ID for field '…'*), and over a non-nullable one the save fails earlier, at the mapping, with Symfony's `InvalidTypeException`. A `Select`'s create-option action refuses the `null` with the error above before `persist()`, unless the class declares a `prePersist` callback or entity listener, when Doctrine's message is what appears. A `prePersist` listener that fills the key saves the record either way.
- **`CanUpdateState` now requires `getValidator()`.** The trait declares `getValidator(): ValidatorInterface` abstract, so an editable column composing it must also compose `CanBeValidated`, which supplies it, or define the method itself. The four shipped editable columns already do. A hand-written column that composed `CanUpdateState` alone fails at class load — at container build when the column is registered as a service, otherwise on its first `make()` — until it does.
- **A decorated association reader is used everywhere.** The create, edit and replicate actions, the resource create page and the editable table cell used to build a plain `AssociationReader` on their entity manager. They now rebind the `sylament_schemas.association_reader` service with `withEntityManager()`, so a subclass or decorator of it runs at every write. A decorator that delegates to another reader must override `withEntityManager()` to rebind the inner one, or it keeps reading through the old entity manager.

## Review fixes (M7 · 11)

- **A nested resource's `getRecordQuery()` holds under its parent.** Under a parent record, the nested edit and record pages, the nested list, a mounted action's record and every intermediate ancestor of a deeper URL used a fresh query of the bare record class narrowed to the parent, so rows an overridden `getRecordQuery()` hides were served there. They now narrow a clone of the resource's own record query to the parent, at any depth. A record query rooted at an alias other than `record` is narrowed under that alias; one naming no root alias is refused with a `LogicException` naming the resource. The scope adds the aliases `sy_owner` and `sy_related` and binds the parameter `sylament_relationship_owner` (`_0`, `_1`, … for a parent keyed by several fields), so an override must not use those names.
- **More record errors show above the form.** A record violation whose deepest owner is a layout component entangling a related record — a `Group`, `Section` or `Fieldset` with `relationship()` — was filed at that component's path, where nothing renders it. It is now filed at the schema's own path (`data`) and renders above the form, or in an action modal's error list — except for such a component inside a relationship repeater item, whose violation is still filed at its path inside the item, where nothing renders it. That covers a class-level violation on the related record, the related record's own constraint on a property the group does not map, and the blank-key refusal when nothing inside the group maps the related record's key field. A class-level violation on a relationship repeater item's record, and one on an item property no item field maps, render above the form the same way. Code that read these messages with `getErrorsForSchemaStatePath('data.<relationship>')` reads `data` instead.
- **A singular relationship refuses a new record whose key is incomplete.** A `Group`, `Section` or `Fieldset` with `relationship()` that constructs a related record whose assigned identifier is still incomplete once it is written onto the owner — a key field over a nullable property left blank or holding whitespace, or one declaring `required(false)` over a non-nullable property holding whitespace — now throws a `LogicException` naming the relationship and the related class inside `getData()`, where the row used to be inserted and could then never be keyed. A single scalar key, and a class with a `prePersist` callback or entity listener, are exempt, as they are for a relationship repeater's items. A shared-key related record whose identifier is the record being saved is refused the same way when that record's own optional single-scalar key holds whitespace. `Schema::validateRecordKey(false)` does not silence it.
- **Custom identifier types.** A custom scalar identifier type whose reader does not read its own PHP value back unchanged now keys rows exactly as `RecordKey::of()` does in attach and associate options, relationship aggregate cells and the paged rows of a query that fetch-joins a collection; before, a lenient reader minted the wrong key with no error, and a strict one threw. A key component the type's reader reads as another value without refusing is now offered to the type's writer once, as a component the reader refuses already was, so such a type's keys decode. The writer is therefore reached for a forged, non-canonical spelling of any type: a custom writer that throws anything other than DBAL's `ConversionException`, or raises a PHP deprecation, surfaces as a 500 where the URL was a 404. A boolean key component must be `0` or `1`; no other spelling ever decoded, and the check keeps one away from PostgreSQL's boolean writer, which would otherwise answer it with a 500.
- **A property no setter can change compares a written number with a held string as a string.** A `readonly` property, or a private one with a getter and no setter, holding a string such as `'05'` now refuses a written int `5` with the `LogicException` naming the field, where the save reported success and wrote nothing. A `Select`, `Radio` or `ToggleButtons` hands a digit option over as an int, so that is where it shows. A held `'5'` still accepts `5`, and a held int still accepts any numeric spelling of itself.
- **A refused create under a many-to-many leaves no record in the owner's collection.** `CreateAction` with `relationship()` and the resource create page under a many-to-many parent add the new record to the owner's collection before saving it. When the save is refused — by the mapping, by the blank-key refusal or inside `persist()`, Doctrine's `EntityMissingAssignedId` included — the record is now taken back out, so a later flush in the same request no longer fails with *A new entity was found through the relationship …*.
