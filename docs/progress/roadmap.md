# Roadmap

The build-order overlay on the parity tables. The [progress tables](README.md)
are the breadth ledger — every Filament surface, audited package by package;
this file orders a thin path through them: which vertical slice to build next,
and toward what demo.

Rows here are **epics** — shippable vertical slices of one to a few PRs each —
not files, so the [one-row-per-file rule](README.md#one-row-per-file-one-file-per-thing)
does not apply. An epic's status describes that slice only, never a component's
full parity — the component's own row in the parity tables keeps that — so
nothing has a status in two places. Epics use the shared
[status vocabulary](README.md#statuses), and the
[same-commit rule](README.md#update-the-trail-in-the-same-commit) extends here:
the commit that finishes an epic flips its row and moves the [Now](#now) cursor.

Milestones prove out in the **demo app** — a separate Symfony project in a
sibling checkout, consuming the bundles through Composer path repositories
(`../sylament`, `../sylament/packages/*`). Epics whose Packages column says
**demo** land there rather than in `packages/`; they carry rows here because
the milestone is not demoable without them, but they never appear in the parity
tables.

Milestones are ordered, not dated, and each is independently demoable: if work
stops mid-M2, M1 still demos on its own.

| 12 | Doctrine `query()` lane | [tables](tables/README.md), [support](support/README.md), **demo** | The second of Filament's two data lanes, beside epic 11's closure lane: a `QueryBuilder` handed to `query()` is the table's data source, and the table itself sorts, searches, paginates and resolves against it. `modifyQueryUsing()` layers scopes on top, and every read gets [a fresh clone of a memoised base](tables/table.md#every-read-clones-a-memoised-base-query) — memoised because the record class, the count query and the page query are three reads of one declaration, cloned because a builder is mutable and one `andWhere()` would otherwise narrow the table permanently. **Which lane a table is on is decided by the escape hatch, not the default**: [`hasQuery()` is `$this->dataSource === null`](tables/table.md#the-query-lane-is-on-exactly-while-no-records-closure-is-set), so a table with **both** is on the records lane — `records()` wins outright, Filament's own precedence — a bare table is on the query lane answering `null` for its query, and `records(null)` is a true reset rather than a one-way switch. The corollary bit twice and is now stated where it can be read: *on the query lane* does not mean *has a query*, so [the filtered-query seams are gated on the lane rather than on a builder being there](tables/has-table.md#the-filtered-query-seam-is-gated-on-the-lane-not-on-the-presence-of-a-builder), which is what keeps a `records()` table from fatalling inside a seam it never asked for. **Identity comes off Doctrine's mapping.** [`resolveQueryRecordKey()` runs ahead of the `id` convention](tables/has-table.md#object-records-are-keyed-by-a-readable-id-rather-than-an-eloquent-key) and, for a record that is an instance of the table's [declared entity](tables/table.md#the-record-class-is-read-off-the-base-querys-root-entity), keys by `ClassMetadata::getIdentifierValues()` — so a `Book` mapped on `code` keys by `code` with nothing configured, which the `id` convention could not do, while a DTO, a `SELECT NEW` projection and every closure-lane record keep the convention unchanged. The guard asks the **table** for its record class and tests with `instanceof` rather than asking Doctrine whether the record's class is mapped, because the obvious API cannot answer: `isTransient()` returns `false` for an anonymous class while `getMetadataFor()` throws for one, so the plainest transient object there is would pass the check and then explode on the metadata read. **Sorting composes three orderings** onto whatever the declaration already carries, [in one method](tables/has-table.md#sorting-composes-the-users-order-the-default-and-the-identifier-tiebreaker): the user's clicked column applies **itself** through `Column::applySort()` (so a `sortable(query:)` closure or a multi-column `sortable([…])` list decides what its own name means), then [`defaultSort()`](tables/table.md#the-default-sort-is-a-secondary-order-and-its-direction-rules-the-tiebreaker) — a *secondary* order, skipped when it names the column the user is already sorting by, resolved through a declared column or through the path resolver when it names a raw path with no column behind it — then `defaultKeySort()`, the identifier tiebreaker that makes a page boundary stable under ties, suppressed by an existing ordering that *ends* in the same field name, Filament's `afterLast('.')` heuristic kept. **Search is the global term, applied to the query.** A blank term is a no-op, a `searchUsing()` closure is the whole assembly (`void`-returning, so a replacement builder from it is discarded — unlike a default-sort closure's, which wins), and otherwise the term splits into words, each word getting its own `Orx` that every globally searchable column and every extra searchable column joins: `OR` within a word, `AND` between words, and a table with nothing searchable adds no `WHERE` at all rather than an empty parenthesis. Two of `PaginationMode`'s [three cases ship](tables/table.md#the-pagination-mode-ships-two-cases-and-two-setters-wait-on-their-features): **Default** pays a `COUNT` for a true total, so a page past the end comes back empty with the total intact rather than clamped — which is what leaves the footer a way back — and **Simple** pays nothing, probing one record past the page and reporting `hasMoreRecords` from whether it arrived. The spec asked for the limit; the fetch-join resolution test overturned it and now pins it, failing with *actual size 1 matches expected size 3* the moment it returns. *And the props dehydrate in their elements' vocabulary.* The browser pass found a table on page 2 snapping back to page 1 when a row's Delete modal was merely cancelled, and the wire named the cause: ux-live-component dehydrates a `LiveProp` through Symfony's `PropertyAccessor`, which prefers a **same-named getter** over the property, so `getTableRecordsPerPage()`'s resolved `int 10` went out against a `<select>` holding `"10"`, the model was permanently dirty, and every live request carried `updated: {tableRecordsPerPage: "10"}` into a hook that resets the page.
