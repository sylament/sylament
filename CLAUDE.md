# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Sylament is a Filament-inspired UI toolkit for Symfony, delivered as a monorepo of nine Symfony bundles under `packages/`: `actions`, `forms`, `infolists`, `notifications`, `panels`, `schemas`, `support`, `tables`, `widgets`. Package names mirror Filament's PHP packages and the same layered dependency idea applies (`support` is the base; `schemas` builds the component model; `forms`/`infolists`/`tables` build on `schemas`; `panels` composes everything). The project is early-stage: `support` and `schemas` are the most built-out, with `forms` and `actions` now shipping real code too; the remaining bundles ship a bundle class plus a placeholder test.

## Reference Filament's implementation

This project is a deliberate Symfony port of Filament. Before designing or extending any component, trait, or API surface, **read how Filament does it first** — their decisions encode years of API ergonomics work and we want to inherit them unless we have a concrete reason to diverge (Symfony idiom, missing dependency, etc.).

Filament's source is installed at `vendor/filament/` (dev dep, never shipped). Useful entry points:
- `vendor/filament/schemas/src/Components/Component.php` — the base component analogous to our future `Sylament\Schemas\Components\Component`.
- `vendor/filament/schemas/src/Components/Concerns/` — single-purpose traits; we will mirror this directory by name as schemas grows.
- `vendor/filament/forms/src/Components/`, `vendor/filament/tables/src/`, etc. — per-bundle equivalents.

When porting, preserve trait names, method names, and the closure-evaluation parameter set (so users carrying Filament mental models stay productive). Translate Laravel idioms to Symfony equivalents (e.g. Eloquent → Doctrine, Livewire → UX LiveComponent, Blade → Twig, `Htmlable` → `Twig\Markup`) but keep the public API shape. The `Htmlable` translation is an escaping contract: wherever Filament types a human-text value as `string | Htmlable | Closure`, we type it `string|Markup|Closure` — plain strings are escaped by templates, `Markup` renders raw (Twig's escaper passes `Markup` instances through untouched, exactly as Blade does with `Htmlable`). When Filament puts a trait on the base class even though only some subclasses use it (e.g. `HasColumns`), assume the choice is for uniform fluent composition and follow suit unless you can articulate why the divergence is worth it.

Preserve Filament's API names by default — migrating users grep for them. Rename only when Filament itself is inconsistent and the better name already exists in their codebase; every rename is recorded in the global rename table, `docs/progress/renames.md` (which also documents the systematic idiom/namespace translations that are *not* renames).

Porting state lives in `docs/progress/` — read `docs/progress/README.md` first: it carries the rules (what earns a file of its own, how to keep the trail in sync) and the status vocabulary every table uses. Per-component state is `docs/progress/<package>/<component>.md`, a surface table over the component's features with per-row detail sections and divergences at the bottom (see `docs/progress/support/component.md` for a filled-in example). Keep these current in the same commit as the code they describe — stale entries are bugs.

## Monorepo wiring (read this before touching deps)

- **One root `vendor/`.** The repo root is a single Composer project. Every bundle is symlinked in via a Composer path repository (`"repositories": [{ "type": "path", "url": "packages/*" }]`) and required as `self.version`. Never run `composer install` inside a sub-package — there is only one lockfile and one vendor at the root. A stray `packages/*/vendor` or `packages/*/composer.lock` is leftover cruft; delete it. Lockfile policy (deliberate): the root `composer.lock` is **not** committed — this is a library monorepo, resolution floats within constraints and CI resolves fresh — while `pnpm-lock.yaml` **is** committed, because the pinned JS toolchain must reproduce the committed `assets/dist` byte-for-byte.
- **All dev dependencies live in the root `composer.json`.** Sub-package `composer.json` files carry production `require` only (their real inter-bundle dependencies). When a bundle needs a new dev tool, add it to the root.
- **Assets are a separate pnpm workspace.** `pnpm-workspace.yaml` globs `packages/*/assets`. Today only `packages/support/assets/` has a `package.json` (`@sylament/support`); the other bundles join the workspace once they get one. PHP and JS are independent dependency graphs that meet only through Symfony AssetMapper.
- `pnpm-workspace.yaml` sets `hoistPattern: []` — transitive deps are NOT reachable by parent-walking. If you get "Module not found" in a workspace, add the dep explicitly to that workspace's `package.json`.
- Each push to `main` (and each tag) is split out to per-package read-only repos under the `sylament` org by the `split-monorepo` job in `.github/workflows/ci.yml`; the split runs only after the `php` and `assets` gate jobs pass (the definition-of-done gates, plus a check that the committed `assets/dist` matches a fresh build). Keep each package self-contained so the split stays valid. Split-repo tests can't run standalone (the Pest bootstrap needs the root vendor) — accepted, since each package's `.gitattributes` export-ignores `/tests` from dist archives anyway.

## Commands

PHP (run from repo root):
- `composer test` — full suite: every bundle's Pest suite + Rector dry-run + PHPStan (level max).
- `composer test:<bundle>` — single bundle's Pest suite, e.g. `composer test:support`. Each invokes `pest -c packages/<bundle>/phpunit.dist.xml --test-directory=packages/<bundle>/tests`.
- `composer test:static` — PHPStan only. `composer test:lint` — PHP-CS-Fixer dry-run. `composer test:rector` — Rector dry-run.
- `composer format` — apply Rector then PHP-CS-Fixer.
- Run one Pest file: `vendor/bin/pest -c packages/support/phpunit.dist.xml --test-directory=packages/support/tests path/to/Test.php` (or use `--filter`).

JS/CSS (run from repo root):
- `pnpm build` / `pnpm watch` — build/watch every asset workspace (`pnpm -r`). `pnpm test:types` — `tsc --noEmit` across workspaces.
- `pnpm format` (Biome write) / `pnpm test:lint` (Biome check). Biome only governs `packages/*/assets/src/**/*.{ts,js}`.
- `support`'s asset `build` runs `clean → tsc --noEmit → esbuild → tailwindcss` into `dist/` (plus a preflight scoping step); the JS build runs through `assets/scripts/build-js.mjs`, which builds every `src/**/*.ts` per-file/unbundled except the entries in its `BUNDLED_ENTRIES` table (today: the dropdown controller, bundling `@floating-ui/dom` with Stimulus external and a license banner composed from the installed package). If `pnpm watch` dies in a non-TTY shell, run `cd packages/support/assets && pnpm watch` directly.

`symfony/asset-mapper` is a root dev dep needed for tests to exercise the AssetMapper path. Without it, bundle `prependExtension` hooks short-circuit (see below) so production consumers aren't forced to install it.

## Core architecture

**Bundle base class.** Every bundle extends `Sylament\Support\SylamentBundle` (an `AbstractBundle`). Its `isAssetMapperAvailable()` guard is why asset-mapper is optional: each bundle's `prependExtension()` registers its `assets/dist` directory into the `framework.asset_mapper.paths` config under the alias `@sylament/<pkg>`, but only when AssetMapper is actually present. Services are wired in `loadExtension()` via the PHP DSL configurator (no XML/YAML service files).

**Closure evaluation — the central pattern.** Almost every configurable value in the API can be either a literal or a closure, mirroring Filament. Two `support` pieces implement this:
- `Sylament\Support\Evaluation\Invoker::call()` reflects a callable's parameters and resolves each in order: explicit `$namedInjections` (by name), explicit `$typedInjections` (by class-string; `self`/`parent` hints are normalized against the declaring class; a `Closure` passed as a named/typed injection *value* is invoked with no arguments and its result injected — Laravel `value()` parity), the `$resolveParameter` callback (`fn (string $name, ?string $typeName)` returning a `ClosureParameter` wrapping the value, or `null` to skip), the DI container (only when `has()` knows the type), the declared default value, then `null` for optional/nullable parameters — otherwise it throws (naming the evaluating class when called through `evaluate()`). A variadic parameter still takes an explicit named/typed/resolver injection when one is supplied; only when none is does it get skipped (leaving `...$x = []`) rather than resolved from the container/default/`null` — so it never receives the spurious `null` Filament passes. There is no `app()->make()`-style auto-wiring of unbound classes (Symfony's container can't).
- `Sylament\Support\Concerns\EvaluatesClosures` is the trait classes use. `evaluate($value, $namedInjections, $typedInjections)` (Filament's parameter names) returns `$value` as-is unless it is a `Closure` instance (a literal string that happens to name a function — `'date'`, `'strtoupper'` — is a value, never invoked), otherwise calls it through `Invoker::getInstance()`, passing a resolver that runs: `resolveDefaultClosureDependencyForEvaluationByName(string $name)` → `resolveDefaultClosureDependencyForEvaluationByType(string $type)` (both overridable, returning `ClosureParameter::make(...)` or `null` to skip) → the instance itself when the parameter is named `$evaluationIdentifier` or type-hints the instance's own class. The schemas base `Component` sets `evaluationIdentifier = 'component'` and `Schema` sets `'schema'`, so `fn ($component) => …` / `fn (Section $component) => …` / `fn ($schema) => …` receive the object being configured.

**Closure typing convention (PHPStan level max, consumer-safe).** Setters take native `Closure` unions with direct assignment and no param PHPDoc — Filament-exact: `public function heading(string|Markup|Closure|null $heading): static { $this->heading = $heading; }`. Never write an arity spec (`callable():T` / `Closure():T`) for a closure whose parameters the Invoker injects: PHPStan cannot express reflection-injected parameters, and a published arity-zero spec false-positives `fn (Section $component) => …` in every consumer's analysis. `evaluate()` carries the only generics: `@template T @param T|Closure $value @return T` — PHPStan infers T by subtracting `Closure` from the prop's union (`string|Closure|null` → `?string`), so props need no docblock beyond native types (array-shaped props keep bare-`Closure` docblocks, with entry types widened to include closure results where those differ, e.g. `HasColumns`). Closure/callable PHPDoc signature specs are not written anywhere — natives + prose carry the contract (a spec would only be truthful for callbacks invoked directly with fixed arguments, and even those go without).

**Static instance pattern.** `EvaluatesClosures` reaches the `Invoker` via `Invoker::getInstance()` so the container doesn't have to be threaded through every component constructor. The mechanism is reusable:
- A class implements `Sylament\Support\DependencyInjection\StaticInstanceInterface` and uses the `HasStaticInstance` trait.
- `StaticInstancePass` (a compiler pass) auto-tags every service definition whose class implements the interface.
- `StaticInstanceRegistry` is constructed with `tagged_iterator(StaticInstanceInterface::class)` and, on `SylamentSupportBundle::boot()`, calls `setInstance($self)` on each tagged service so the static accessor works.
- Tests call `StaticInstanceRegistry::unsetStaticInstances()` in `tearDown` (see `packages/support/tests/TestCase.php`) so state doesn't leak between cases.
  `Invoker`, `ComponentManager`, and `IconManager` use the pattern today. Reuse it for future singleton-shaped services that need to be reachable from non-DI contexts.

**Global configuration.** `Sylament\Support\Components\ComponentManager` is the Filament `configureUsing()` port: `X::configureUsing($closure)` (via the `Configurable` trait) registers a class-keyed closure, and every `make()` runs `configure()`, which walks the class hierarchy root-first — calling `setUp()` at its declaring class's position, each class's registered closures after it, and `isImportant` closures last. `during:` scopes a registration to one closure's run; otherwise `configureUsing()` returns a removal closure. `ComponentManager::resolve()` returns the booted static instance or lazily creates one outside DI (the service is defined with `factory(ComponentManager::resolve(...))` so both are the same object); Unit suites unset it in a `tests/Pest.php` `afterEach` hook.

**Component model (today: in `support`).** The abstract base is `Sylament\Support\Components\Component`, which composes `EvaluatesClosures` and `Configurable`. `Sylament\Support\Components\ViewComponent` extends it with Twig-backed rendering: `template()` / `templateData()` setters (each closure-evaluable), `getTemplate()` / `getTemplateData()`, and `render(Environment $twig)`. `Sylament\Support\Twig\Extension\ComponentExtension` exposes a `renderComponent(component)` Twig function backed by `ViewComponent::render()`. Attribute rendering in templates goes through `Sylament\Support\Twig\Extension\AttributeExtension`: `attrs(...sources)` is the `html_attr()` replacement backed by `ComponentAttributeBag` (later scalars win, class/style token lists append; class values take strings/conditional maps directly), and `classes()` builds a token list for the one place a foreign bag renders attributes (ux-twig-component's `attributes.defaults()`). `twig/html-extra` is not a dependency and its helpers are banned in templates (enforced by schemas' `TemplateConventionsTest`) — one attribute implementation, auto-registered by the bundle. Higher bundles subclass these (`schemas`' `Schema` and `Component` do today; the form fields will follow). Favor adding a focused `Concerns/Has*` trait over widening an existing class. Template context contract: `render()` passes `component` (the instance), then the `getExtraTemplateData()` class hook, then user `templateData()` (wins on key collision). Keep `getExtraTemplateData()` minimal — only values the template can't get from a single getter call (generated ids, fallback chains, cross-trait policy like Section's `collapsible`, child schemas needing constants or mutations); anything that is one getter is read in the template as `component.x`. It is the Twig-side port of Filament v5's `toEmbeddedHtml()` local-variable preamble — don't mirror plain getters into it.

**Twig components and template layout.** Every bundle's `templates/components/` holds two kinds of file, and the shape tells you which: `<Name>/index.html.twig` is an **anonymous** Twig component resolved by ux-twig-component's finder and invoked as `<twig:Sylament<Pkg>:<Name> />` (support's `Modal`/`Button`/`Icon`/`IconButton`/`Section`/`Dropdown`, forms' `FieldWrapper`); a flat `<name>.html.twig` is a template referenced **from PHP or an include** and never as a tag — a `ViewComponent::$template` (schemas' five, forms' `TextInput`/`Textarea`, actions' `button-action`/`grouped-action`/`action-group`), an `{% include %}` target (actions' two `action-group/` trigger templates, chosen by `ActionGroup::getTriggerTemplate()`), or an `#[AsTwigComponent(template:)]`. Anonymous is the default: prefer it unless the component needs PHP, and prefer a component over `{% include %}` for anything a template renders — `{% props %}` states a contract an include's `with {}` only implies. The one cost: the `<twig:>` HTML syntax has no `only` (the `{% component %}` tag does), so a component inherits the caller's context where `{% include … only %}` is isolated; declare every prop and don't lean on inherited variables. `actions`' [`Modals`](packages/actions/src/Twig/Components/Modals.php) is the one **class**-based component today, because it must resolve its host live component by walking ux-twig-component's `ComponentStack` — inside a Twig component `this` is that component, not the host, so no template-scope approach works at arbitrary nesting depth (reasoned out in `docs/progress/actions/has-actions.md`). A class component is a container service, so its bundle registers and `->autoconfigure()`s it in `loadExtension()` (injecting `ux.twig_component.component_stack` by **service id** — it has no class alias). **Dependency declaration.** Each package declares what its own `src/` and `templates/` need, *even when a sibling already pulls it in* — every package requires `sylament/support`, but the CI split publishes each one standalone, so inheriting through a sibling is how a split repo silently breaks (`actions` fatally `use`d `ComponentToolsTrait` while only `schemas` declared `symfony/ux-live-component`). Two things count as needing it: a PHP symbol imported by `src/` (`Modals` type-hints `AsTwigComponent`/`ComponentStack`), or a Twig extension a shipped template cannot **parse** without (`{% props %}` in support's and forms' component templates). Conversely, never push a dependency down into `support` that support itself doesn't use — it references `Symfony\UX\LiveComponent` and `symfony/string` nowhere, so those stay on `actions`/`schemas`/`forms`. The five placeholder bundles import only `SylamentBundle`, so `sylament/support` alone is complete for them; this rule adds nothing to a package that uses nothing.

Two deliberate omissions, so their absence reads as a decision rather than an oversight: **`twig/twig`** is not declared by `actions`/`forms`/`schemas` despite direct `Twig\Markup` use (support declares it and Twig cannot leave the graph), and **`symfony/dependency-injection` / `symfony/http-kernel`** are declared nowhere despite every bundle extending `AbstractBundle` and wiring services — both are treated as ambient, arriving with `symfony/framework-bundle`. Revisit either only if a split package is ever consumed without framework-bundle.

## Conventions

- PHP: `declare(strict_types=1)` everywhere; PHPStan **level max** must stay green (only `trait.unused` is globally ignored; `reportUnmatchedIgnoredErrors` is on, so stale ignores fail the run — no baseline file exists). PSR-4 namespace `Sylament\<Bundle>\` → `packages/<bundle>/src/`, tests `Sylament\<Bundle>\Tests\` → `packages/<bundle>/tests/`. Tests are Pest. Formatting is PHP-CS-Fixer + Rector — run `composer format`, don't hand-format.
- Helper functions: `Sylament\Support`-namespaced functions in `packages/support/src/helpers.php` (composer `files` autoload; import with `use function`). `filled()` / `blank()` mirror Laravel's, except `Twig\Markup` is special-cased to text semantics: it is `Countable` (counts its characters), so Laravel's count-first order would call a whitespace-only `Markup` filled, while Laravel's `HtmlString` isn't `Countable`. Other `Countable+Stringable` objects (Doctrine collections) keep Laravel's count semantics. Two further deliberate deltas: `blank()` trims with `mb_trim`, so NBSP/em-space-only strings count as blank (Laravel's byte `trim` doesn't); and Laravel's `instanceof Model → filled` short-circuit has no Doctrine equivalent here, so a `Countable`-empty entity reports blank. Future Filament helper ports (`is_slot_empty`, …) go in this file. After editing a sub-package `composer.json`, run `composer update sylament/<pkg>` — plain `dump-autoload` reads the stale lock metadata for path packages.
- Test layout (canonical, lived out in `support` and `schemas`): each bundle's `tests/` is split into buckets — `Unit/` for tests with no kernel boot (pure logic, compiler passes against a hand-built `ContainerBuilder`, trait behavior with fixture classes), `Integration/` for tests that boot the kernel or hit the container, plus an optional `Architecture/` bucket for repo-convention guard tests that scan files rather than exercise a SUT (e.g. schemas' `TemplateConventionsTest`; no kernel, Pest default base). Inside `Unit/` and `Integration/`, **mirror the `src/` tree exactly**: `src/DependencyInjection/Compiler/StaticInstancePass.php` → `tests/Unit/DependencyInjection/Compiler/StaticInstancePassTest.php`, `src/SylamentSupportBundle.php` → `tests/Integration/SylamentSupportBundleTest.php`. `tests/Pest.php` attaches `TestCase` (the `KernelTestCase` subclass) only to `Integration/`; Unit tests use Pest's default base, and the Unit blocks in both `tests/Pest.php` files install/unset the default `Invoker` static instance plus the manager teardowns — don't re-add per-file hooks. Test file names match the SUT (`FooTest.php` for `Foo.php`). Support's shipped Twig components (Icon, IconButton, Section) are render-tested from **schemas'** Integration suite — only schemas' fixture Kernel registers TwigComponentBundle/StimulusBundle — so `composer test:support` alone doesn't exercise those templates; deliberate (docblock-noted there), revisit only if support grows its own Twig-component test kernel. The other seven bundles currently ship a placeholder `Feature/ExampleTest.php` — adopt the Unit/Integration split as real tests land, don't entrench `Feature/`.
- Fixture layout: `tests/Fixtures/` mirrors `src/` for per-test fixture classes (e.g. fixtures supporting `src/DependencyInjection/` tests live in `tests/Fixtures/DependencyInjection/`). Global test-app infrastructure (the `Kernel`, fixture service-config files) stays at the root of `tests/Fixtures/`. Don't dump everything flat — put each fixture next to the subsystem it exercises so it's findable as the suite grows.
- Test Kernel wiring: the test `Kernel` PSR-4-loads everything under `tests/Fixtures/` recursively with `autowire + autoconfigure` defaults (excluding `Kernel.php` itself). Adding a new fixture means dropping a class in the right `Fixtures/` subfolder — never edit the Kernel to register individual fixture services. Services stay private by default; `KernelTestCase::getContainer()` returns the `test.service_container` which exposes privates to tests, so you rarely need anything public. When a fixture genuinely must be public in the real container, opt in with `#[Autoconfigure(public: true)]` on the fixture class itself — never widen the Kernel defaults. If a fixture needs special construction, write a small config (e.g. `Fixtures/services_special.php`) and `import()` it from the Kernel rather than hand-wiring inline.
- Pest tests: inside `it()` / `test()` closures, reach static `KernelTestCase` helpers through `$this::` (e.g. `$this::getContainer()`, `$this::bootKernel()`) — never `static::` or `self::`. Pest binds `$this` to the configured `TestCase`, so `$this::foo()` resolves to that class's static method; `static::foo()` resolves against the anonymous closure scope and is wrong.
- Pest tests: don't call `bootKernel()` explicitly — `KernelTestCase::getContainer()` auto-boots when no kernel is booted. Just call `$this::getContainer()->get(...)` directly. Only boot explicitly when you need to pass options (`$this::bootKernel(['environment' => 'foo'])`) or grab the kernel object itself.
- TS: strict mode, `target` ES2022, ESM, bundler resolution (`tsconfig.base.json`). Biome enforces `useImportType`, `useConst`, and bans `any` and non-null assertions (`!`) as errors. Relative imports must carry the compiled `.js` extension (`useImportExtensions` with a ts→js mapping): esbuild builds without `--bundle`, so specifiers ship verbatim to the browser and an extensionless import would pass `tsc` but 404 at runtime. Stimulus is a peer dep pinned to `^3` via workspace overrides. `@floating-ui/dom` is a regular dependency bundled into `dist` via the `BUNDLED_ENTRIES` table in `scripts/build-js.mjs`, never resolved by consumers.
- CSS: semantic `sy-<pkg code>-*` classes only in Twig (never utilities — template scanning is off), e.g. `sy-fo-input`, `sy-sc-grid`; every component template root also carries the bare `sy` marker class; `@apply` authoring in `packages/<pkg>/assets/src/styles/components/<name>.css`; dynamic per-instance values via inline `--sy-*` CSS variables; colors through the `--sy-*` runtime tokens; Tailwind preflight is never shipped page-wide — `support`'s build generates a `.sy`-scoped copy from the installed Tailwind (`assets/scripts/scope-preflight.mjs`). Full contract: `docs/styling.md`.
- Prefer the idiomatic construct over manual mechanics, and actively hunt for one whenever code reads noisy or repetitive — the language/library usually ships a purpose-built syntax (e.g. Twig hash spread `...(x ?: {})` replaced `|merge(x ? x.toArray() : {})` chains; StimulusBundle's Twig helpers replaced hand-concatenated `data-*` attribute strings). Verify the candidate against the installed vendor source before relying on it.

## Definition of done

- `composer test` green (Pest + Rector dry-run + PHPStan max).
- `pnpm test:types` and `pnpm test:lint` green.
- `composer format` applied; no hand-formatting.
