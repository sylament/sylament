# Translations

Systematic translations that follow the conventions in [CLAUDE.md](../../CLAUDE.md).
They are **not** renames and must not be added to the table above.

## Idiom

| Laravel / Filament | Sylament | Example |
| --- | --- | --- |
| `Htmlable` | `Twig\Markup` | — |
| Livewire | UX LiveComponent | `getLivewire()` → `getLiveComponent()`, `livewireProperty()` → [`liveComponentProperty()`](schemas/tabs.md), `Schemas\Components\Livewire` → [`LiveComponent`](schemas/live-component.md), `getLivewireKey()` → [`getLiveComponentKey()`](schemas/live-component.md#the-host-id-is-minted-by-the-host-because-ux-has-no-stable-component-id), `getSubmitFormLivewireMethodName()` → [`getSubmitFormLiveComponentMethodName()`](panels/form-actions.md#one-method-name-drives-both-the-form-element-and-the-submit-action). The vocabulary reaches parameters and closure signatures too: `hiddenOn(string \| array $livewireComponents)` → [`hiddenOn(string\|array $hosts)`](tables/column.md#surface), and the `HasTable $livewire` its generated closure receives → `InteractsWithTable $liveComponent` — on **both** traits named `CanBeHidden`, the column tier's and the filter tier's. `$hosts` rather than `$liveComponents` because what the argument takes is a list of host **class-strings** to match with `instanceof`, which is what the port's own [`hiddenOn()`](tables/column.md#surface) prose calls them. |
| Livewire's `WithPagination` trait (`gotoPage()`, `nextPage()`, `previousPage()`, `resetPage()`, the query-string page name) | a `#[LiveProp] int $tablePage` on the host and one `#[LiveAction]` that moves it | `gotoPage($page, $pageName)` → [`gotoTablePage(page)`](tables/host-can-paginate-records.md#gototablepage-replaces-livewires-paginator-trio) |
| Eloquent | Doctrine | — |
| `Carbon\CarbonInterface` / `Illuminate\Support\Carbon` | `DateTimeInterface` / `DateTimeImmutable` | `minDate(CarbonInterface \| string \| Closure \| null $date)` → [`minDate(DateTimeInterface\|string\|Closure\|null $date)`](forms/date-time-picker.md). Carbon is a Laravel-ecosystem package with no place here; every Filament signature naming a Carbon type takes the PHP interface it extends, and a value the port constructs is a `DateTimeImmutable`. The lost surface is Carbon's fluent parsing and formatting sugar, which the consumers so far replace with `DateTimeImmutable::createFromFormat()` and `->format()` ([the cast](schemas/date-time-state-cast.md), [the pickers](forms/date-time-picker.md)) — and, where a Carbon **method** has no `DateTime` equivalent at all, with a port: `$state->diffForHumans()` becomes [`Sylament\Support\diff_for_humans($date, $now)`](support/helpers.md#diff_for_humans-is-a-carbon-port-not-a-carbon-dependency), which walks Carbon's own cascade at its `$parts = 1` default. The helper takes `$now` explicitly where the method reads the clock, so it stays pure; that is the only shape difference. |
| Eloquent `Builder` | Doctrine `QueryBuilder` | `query(Builder $query)` → [`query(QueryBuilder $query)`](tables/has-query.md#every-read-clones-a-memoised-base-query); `modifyQueryUsing(fn (Builder $query) => …)` → `fn (QueryBuilder $query) => …`. Both are the query object each ORM composes a select in, so the parameter and property types translate wholesale wherever a Filament signature names `Builder`. The two are not interchangeable in shape — Doctrine's carries its `EntityManagerInterface` and a class-string FROM clause where Eloquent's carries a model instance — which is why `getQueryEntityManager()` below has no Filament counterpart and why `getRecordClass()` reads a root entity where `getModel()` read an instance. |
| Blade view | Twig template | `view()` → `template()`, `viewData()` → `templateData()`, and the `*_VIEW` constants that name one — `Action::ICON_BUTTON_VIEW` → [`ICON_BUTTON_TEMPLATE`](actions/action.md), the constant `HasExtraItemActions` stamps onto an extra item action |
| Blade component scope inheritance (`$this` is the Livewire component) | an explicit host — resolved from the Twig component stack, or passed as a prop | `<x-filament-actions::modals />` → `<twig:SylamentActions:Modals />` (see [modals.md](actions/modals.md#the-modals-renderer-resolves-its-host-from-the-render-stack-not-from-template-scope)) |
| A Livewire event's `livewireId` payload key | dropped — a browser event is scoped by the live root that dispatched it | `dispatch('form-validation-error', livewireId: $this->getId())` → `dispatchBrowserEvent('form-validation-error', ['schemaKey' => …])`, and `reset-schema-component-state`'s `{livewireId, schemaKey}` → `{schemaKey}`. Both event **names** carry over unchanged; only the payload translates, so neither is a rename. Livewire broadcasts an event to every component on the page, so the id is how a listener recognises its own host; these travel as **browser** events dispatched on the host's own root, and the listeners compare `event.target` with `this.element.closest('[data-controller~="live"]')` — the host that dispatched is the host that owns the schema — so the id has nothing left to disambiguate. `form-validation-error` gains `schemaKey` in the trade, which Filament's carries nowhere: over there the reveal walks the DOM from the first error, where here the root controller has to know which schema the failure belongs to. |
| Alpine.js | Stimulus | `x-data` / `x-on:` → a controller under `packages/*/assets/src/controllers/`, wired with StimulusBundle's Twig helpers |
| A `window` event broadcast to reach one component among many | a method on the owning Stimulus controller, which its own targets scope | Filament's `repeater-collapse` / `repeater-expand` are dispatched on `window` and keyed by state path, so every repeater on the page hears them and matches itself; here the collapse-all / expand-all triggers bind straight to `collapseAll` / `expandAll` on the repeater's own controller, which iterates its `item` targets. Stimulus scopes targets to the nearest controller of the same identifier, so a nested repeater's items are never touched and two cards rendering the same state path cannot cross-talk. The events have no Sylament names because they no longer exist; nothing public is renamed. |
| `fi-*` classes | `sy-*` classes | `fi-icon-btn` → `sy-icon-btn`, `fi-disabled` → `sy-disabled`, `fi-sortable-ghost` → `sy-sortable-ghost` (the class handed to SortableJS through `ghostClass`, as [a bundled library's classes are](../internals/styling.md#why-is-a-bundled-library-styled-under-a-sylament-class)) |
| `filament.*` route names | `sylament.*` route names | `filament.{panel id}.pages.{slug}` → `sylament.{panel id}.pages.{slug}`, so `filament.admin.pages.dashboard` → `sylament.admin.pages.dashboard` ([`Page::getRouteName()`](panels/page.md) builds it; the panel id and the page slug are untouched). The vendor prefix travels with the vendor, exactly as `fi-` → `sy-` does above, and for the same reason: a route name is a string a migrating user greps for and types into `path()` calls, so it changes once and wholesale rather than page by page. |
| A Laravel storage disk | A Flysystem storage ([league/flysystem-bundle](../../vendor/league/flysystem-bundle)) | `disk('public')` → `disk('public.storage')` ([file-upload.md](forms/file-upload.md#disk-names-a-flysystem-storage-and-there-is-no-publiclocal-swap)). The method keeps Filament's name — it is public API a migrating user greps for — and only the *value* translates: where Laravel names a `filesystems.disks` key, Sylament names a flysystem storage service, collected by support's [`FilesystemRegistry`](support/filesystem-registry.md) off the bundle's own `flysystem.storage` tag. The toolkit-wide default moves the same way, from `filament.default_filesystem_disk` to `sylament.default_filesystem_disk`. |
| `Str::uuid()` | `Uuid::v4()->toRfc4122()` ([symfony/uid](../../vendor/symfony/uid)) | The state cast that keys a file map by uuid ([`FileUploadStateCast`](../../packages/schemas/src/State/Casts/FileUploadStateCast.php)). Laravel's helper answers a `Ramsey\Uuid` object that stringifies to the RFC 4122 form; the Symfony factory answers a `Symfony\Component\Uid\Uuid`, so the spelling is explicit rather than implicit. `Str::ulid()` translates the same way, to `new Ulid()->toBase32()`, which is what names a stored upload. |
| A `Str::` macro Filament declares in its service provider | a function in [`Sylament\Support`'s `helpers.php`](support/helpers.md) | `Str::sanitizeUrl($url)` → `sanitize_url($url)`, `Str::sanitizeCssColor($color)` → `sanitize_css_color($color)`. There is no `Str` class here to extend and no provider to boot it in, so a macro whose body is **pure** lands as a helper under the snake_case naming the rest of that file uses. The body ports verbatim, `// Security:` comments included; only the call site changes shape. A macro that needs a *service* goes onto the service or Twig extension owning the dependency instead — [`generate_icon_html()`](support/helpers.md#generate_icon_html-moved-to-the-twig-extension) is the precedent, and the reason `helpers.php` is pure-only. |
| `Arr::first()` | `array_first()` (PHP 8.5 native) | The same cast's single-file read. The language grew the function Laravel's helper existed for, so there is nothing to port to [`helpers.php`](support/helpers.md) — the no-callback arm of `Arr::first()` is `array_first()` exactly, including the `null` for an empty array. |
| Laravel's translator (`__('filament-…::…')` keys, `translateLabel()`) | an English literal | Every user-facing string ships as Filament's `en` text, because i18n is [deferred toolkit-wide to one dedicated pass](../internals/i18n.md) rather than ported per component. Each detail file lists the literals it adds in a "literals, not translation keys" divergence ([file-upload.md](forms/file-upload.md#literals-not-translation-keys)), so that pass can find every one. |

CSS class names are not a flat prefix swap: bundles above support insert a package code (`sy-fo-input`, `sy-sc-grid`), support-level classes carry none (`sy-icon-btn`), and every template root also gets the bare `sy` marker class.
Why: [`docs/internals/styling.md`](../internals/styling.md#why-do-templates-carry-only-semantic-classes).

The same `fi-` → `sy-` translation covers **CSS custom properties**, and there it is load-bearing rather than cosmetic.
Filament's colour variables are unprefixed — `--primary-600`, `--color-600`, `--text`, `--dark-hover-bg` — and Sylament's are `--sy-primary-600`, `--sy-color-600`, `--sy-text`, `--sy-dark-hover-bg`, whether they are written in a stylesheet, emitted inline by `ColorManager::getComponentCustomStyles()`, or emitted into a `<style>` element by `sylamentStyles()`.
Custom properties inherit and Sylament embeds into a page it does not own, so one `:root { --text: … }` in the host app would otherwise repaint every Sylament component.
The exception is the Filament-*verbatim* grid variables (`--cols-lg`, `--col-span-default`), which stay unprefixed on purpose — [styling.md](../internals/styling.md#why-are-per-instance-values-inline-variables) draws that line.
Measured porting cost of the prefix, and the reasoning: [color-manager.md](support/color-manager.md#every-emitted-custom-property-carries-the---sy--prefix).

## Namespace segments

Segments carry over from Filament **verbatim** — `Components\`, `Enums\`, `Exceptions\`, `Concerns\`, `Contracts\`, `Icons\` and the rest all keep Filament's spelling, so `Filament\Support\Components\Concerns\` is `Sylament\Support\Components\Concerns\`.
Exactly two segments change, each only because the thing it named was replaced or has no Symfony counterpart at all:

| Filament | Sylament | Why |
| --- | --- | --- |
| `View\` | `Twig\` | The Blade → Twig idiom — the template engine itself changed. Laravel's `ComponentAttributeBag` and Filament's `SupportIconAlias` both live in `Sylament\Support\Twig\`. |
| `Http\Controllers\` | `Controllers\` | Only the Laravel `Http\` tier drops — Symfony has no `Http/` application layer (middleware became event listeners, and a response is Symfony's own object), so the segment names nothing here. The plural `Controllers` is Filament's spelling kept verbatim, matching the repo's plural object directories (`Pages\`, `Components\`, `Exceptions\`). Symfony's own bundles use singular `Controller\` (FrameworkBundle, WebProfilerBundle); the plural is a deliberate in-repo-consistency choice, the same trade the `Exception\` note below records. |

No segment is renamed for style.
Symfony's own habit of singular `Exception\` (its components and bundles both use it) is **not** followed here: matching Filament costs a migrating user nothing to learn, and one carve-out is worse than none.

Three namespaces **leave `Components\`**, because what they hold is not part of the component tier — neither a component, nor a concern or contract of one.
Two of them land under `State\` rather than at the root, filing beside the [`PropertyAccessor`](schemas/property-accessor.md) they read and write through; each drops the segment that `State\` now says for it (`StateCasts` → `Casts`, `Utilities` → nothing, since the word named no category):

| Filament | Sylament | Holds |
| --- | --- | --- |
| `Filament\Schemas\Components\StateCasts\` | `Sylament\Schemas\State\Casts\` | `StateCast` and its implementations — value objects that transform state |
| `Filament\Schemas\Components\Utilities\` | `Sylament\Schemas\State\` | `Get` / `Set` — the closure-injected state accessors |
| `Filament\Support\Components\ComponentManager` | `Sylament\Support\Configuration\ComponentManager` | The `configureUsing()` registry — an engine, filed by capability like `Evaluation\Invoker`, not beside what it configures |

A migrating user importing `Filament\Schemas\Components\Utilities\Get` will not find it by prefix swap alone, which is why these are recorded here rather than left to the verbatim rule.

The colour tier leaves `View\` for the same reason, and is the one place the `View\` → `Twig\` translation above is deliberately **not** applied:

| Filament | Sylament | Holds |
| --- | --- | --- |
| `Filament\Support\View\Components\` (the policy objects) | `Sylament\Support\Colors\Components\` | `BadgeComponent`, `ButtonComponent`, … — the per-element contrast policies |
| `Filament\Support\View\Components\ColorMaps\` | `Sylament\Support\Colors\Maps\` | `ComponentColorMap` and the two specialised resolvers |
| `Filament\Support\View\Components\Contracts\` | `Sylament\Support\Colors\Contracts\` | `HasColor` (the `getColorMap()` one) and `HasDefaultGrayColor` |
| `Filament\Schemas\View\Components\` | `Sylament\Schemas\Colors\Components\` | schemas' `TextComponent` and `IconComponent` |
| `Filament\Tables\View\Components\Columns\` | `Sylament\Tables\Colors\Components\` | tables' `TextColumnComponent\ItemComponent` and `TextColumnComponent\ItemComponent\IconComponent` |

`Sylament\Support\Twig\Components\` — where the translation would have put them — already means a class-backed **renderable** Twig component, the shape actions' `Modals` has.
A colour policy is never rendered and has no template, so it is filed by capability at `src/` level like `Evaluation\Invoker` and `Configuration\ComponentManager`.
Class names, including the nesting (`DropdownComponent\ItemComponent`, `TextColumnComponent\ItemComponent\IconComponent`), are Filament-verbatim to any depth; only the leading segments move.
Detail: [color-policies.md](support/color-policies.md#the-tier-is-filed-under-colors-not-under-twigcomponents).

The tables row absorbs one more segment than the others, and that is the whole of the difference: Filament groups its tables policies under a `Columns\` directory which is the **only** child `View\Components\` has there, so it separates nothing from anything and is dropped into the leading segments rather than carried.
Everything below it is untouched — an icon policy that belongs to the text column's item is `TextColumnComponent\ItemComponent\IconComponent` here exactly as it is there, the same nesting support's still-blocked [`DropdownComponent\ItemComponent\IconComponent`](support/color-policies.md#surface) already carries.
The nesting is a class-string a consumer types into `colorAttributes()`, so a flatter spelling would be a rename in everything but name.

Support-level traits split by **who composes them**, so `Filament\Support\Concerns\` has two destinations:

| Filament | Sylament | Which traits |
| --- | --- | --- |
| `Filament\Support\Concerns\` | `Sylament\Support\Components\Concerns\` | Everything only a component composes — `HasIcon`, `HasColor`, `HasExtraAttributes`, … and `Configurable`, whose sole consumer is `Component` |
| `Filament\Support\Concerns\` | `Sylament\Support\Concerns\` | `EvaluatesClosures` alone |

`EvaluatesClosures` stays at root against that rule for a reason that is checkable in Filament rather than a matter of taste: of its three direct importers there, two — `Colors\ColorManager` and `TimezoneManager` — are plain manager classes, not components.
That is no longer a prediction: [`Sylament\Support\Colors\ColorManager`](../../packages/support/src/Colors/ColorManager.php) composes the trait today, to evaluate a `Closure` palette registration, and it is not a component — so a trait under `Support\Components\Concerns\` would be the wrong import.
The hold stands on a real consumer now rather than on Filament's, and moves only if that consumer goes away.

One trait moves **down a package** for the same who-composes-it reason, except that here the layering forces it rather than merely suggesting it:

| Filament | Sylament | Which trait |
| --- | --- | --- |
| `Filament\Forms\Components\Concerns\` | `Sylament\Schemas\Components\Concerns\` | `CanBeMarkedAsRequired` alone |

Filament hosts the trait in forms yet imports it from schemas' `Fieldset` (`vendor/filament/schemas/src/Components/Fieldset.php`) — an upward import from schemas into forms.
Here `forms` depends on `schemas`, so that direction cannot be reproduced, and the trait has to sit at or below the lower package for both consumers to reach it.
Nor is that a style question: the CI split publishes each package standalone, so a package leaning on a symbol only a sibling declares breaks the moment it is installed on its own.
See [schemas/can-be-marked-as-required.md](schemas/can-be-marked-as-required.md).
The class name, methods and body are unchanged, which is why this is a relocation rather than a rename.

One **component** moves the other way for the same reason, and it is the same Filament file that forced the trait down:

| Filament | Sylament | Which class |
| --- | --- | --- |
| `Filament\Schemas\Components\FusedGroup` | `Sylament\Forms\Components\FusedGroup` | `FusedGroup` alone |

The criterion in both directions is **the lowest package that reaches every symbol the thing needs**.
For a trait two tiers compose, that is the lower package, so `CanBeMarkedAsRequired` went down.
`FusedGroup` imports three forms concerns — `CanBeMarkedAsRequired`, `HasExtraFieldWrapperAttributes`, `HasHelperText` — plus `Forms\Components\Field` for its error walk, and what it renders is forms' field-wrapper chrome; nothing it needs can move down with it, so the lowest package reaching all of it is `forms` and the class goes up.
Filament can host it in schemas because Laravel ships every Filament package together; the CI split here publishes each one standalone, so a `sylament/schemas` importing a forms symbol breaks on install.
Class name, factory, methods and behaviour are unchanged; only the namespace moves, taking the CSS class code with it — `fi-sc-fused-group` becomes `sy-fo-fused-group`, the [component code](../internals/styling.md#why-do-templates-carry-only-semantic-classes) naming the package that ships the component rather than the vendor directory the rules were copied from.
See [forms/fused-group.md](forms/fused-group.md#fusedgroup-lives-in-forms-not-schemas).

Two traits move **up** out of `support`, and the same layering argument runs the other way for them — they are two of the traits Filament's `Column` composes from `Support\Concerns\`.
Both reach Doctrine, and `support` depends on neither Doctrine nor schemas — deliberately, since [nothing is pushed down into support that support does not use](../../.claude/rules/manifests.md) — so hosting them there would mean either dragging the ORM into the base package for one consumer or splitting one read across two packages:

| Filament | Sylament | Which trait |
| --- | --- | --- |
| `Filament\Support\Concerns\HasCellState` | `Sylament\Tables\Columns\Concerns\HasCellState` | The cell read, which goes through schemas' `PropertyAccessor` — [why](tables/has-cell-state.md#hascellstate-is-relocated-into-the-column-tier) |
| `Filament\Support\Concerns\CanAggregateRelatedModels` | `Sylament\Tables\Columns\Concerns\CanAggregateRelatedRecords` | The six aggregate declarations, read by tables' own [batched aggregate query](tables/has-query.md#an-aggregate-is-a-batched-side-query-and-a-hidden-subselect-never-a-select-on-the-page-query) |

Filament's placement pays off for a **second** consumer in both cases — `Actions\Exports\ExportColumn` composes each of them — and that class is unported, since the port has no export surface yet.
When it lands, both move to the lowest package both consumers reach, which is `schemas` (`tables` and `actions` each require it) and still not `support`.
The first is a pure relocation; the second is [also renamed](renames.md#renames), which is why it has a table row of its own and this one does not repeat it.

## Names with no Filament source

Methods, classes and events that exist only here, because a port needed behaviour Filament has no member for.
Nothing to rename from, so they are listed rather than mapped — and listed at all so a migrating user who greps Filament for the name and finds nothing knows the absence is real.

| Sylament | On | Why it is not a rename |
| --- | --- | --- |
| [`nullWhenBlank()`](schemas/has-nullable-branch.md#a-declared-branch-is-nulled-whole-before-its-leaves-are-written) | `Sylament\Schemas\Components\Concerns\HasNullableBranch` | Declares a container an optional branch of the record graph, so a blank one is written as `null` instead of being built empty. The nearest Filament member is `relationship(condition:)`, and it is not the same call under another name: its **polarity is inverted** (`condition:` true means *save*, this means *discard*), it carries no built-in blank test — a Filament user hand-writes the emptiness check at every call site — and it is scoped to an Eloquent relationship where this is scoped to a declared state path. Renaming `condition:` onto it would map a Filament call to a Sylament call that does the opposite. |
| [`isBlankStateValue()`](schemas/has-nullable-branch.md#the-built-in-blank-test-asks-the-branchs-own-leaves) | `Sylament\Schemas\Components\Concerns\HasNullableBranch`, overridden on `Checkbox` / `Toggle` | The blank test each declared leaf answers for the branch pass, so a field whose cast never dehydrates null (an untouched checkbox rests at `false`) can still read as blank. Filament has no branch pass at all — `nullWhenBlank()` above is Sylament-only — so there is nothing for the predicate it consults to be renamed from. |
| [`ownsRecordSubtree()`](schemas/belongs-to-record.md#a-component-can-own-its-whole-record-subtree) | `Sylament\Schemas\Components\Concerns\HasChildComponents` | Marks a component whose own dehydrated value is the record value for every path beneath it, so the record path map treats it as a leaf and drops the paths its descendants declare. The map is Sylament-only — Filament maps by wholesale array assignment on the record, so it never had to ask which component speaks for a path and has no member to rename from. |
| [`itemsAs()`](forms/repeater.md#the-item-cast-fires-at-the-repeaters-two-pipeline-boundaries-not-in-the-generic-seam) | `Sylament\Forms\Components\Repeater` | Declares the item class a repeater's items round-trip as, so the record property holds identity-free value objects while the live bag keeps arrays. Filament's nearest member is `relationship()`, and mapping one onto the other would promise semantics this deliberately excludes: `relationship()` is identity-keyed Eloquent mapping with the responsibilities inverted — it maps item state onto *managed records*, deciding which row is which entity and what happens to the ones that vanished, where this constructs a fresh value object per item every save and never asks. Identity is [`relationship()`'s](forms/repeater-relationship.md#a-relationship-repeater-keys-its-items-by-identity-and-diffs-the-collection), which shipped with the Doctrine relation layer and is [exclusive with `itemsAs()`](forms/repeater-relationship.md#the-relationship-family-loses-its-caches-its-lifecycle-hooks-and-its-query-scope) in either declaration order. |
| [`ObjectStateCast`](schemas/object-state-cast.md) | `Sylament\Schemas\State\Casts` | The per-value transform behind `itemsAs()`: an array's keys in, a fresh instance of a declared class out, and back. Filament ships no object-constructing cast anywhere in `Components/StateCasts/` — its answer to object-shaped repeater state is `relationship()`, per the row above — so the class name follows the shipped cast family (`BooleanStateCast`, `OptionStateCast`) rather than renaming anything. |
| [`getOptionComparisonState()`](forms/has-options.md#the-option-vocabulary-is-normalized-once-rather-than-per-template) | `Sylament\Forms\Components\Concerns\HasOptions` | The state an option template compares its own `value` against, normalized into the option vocabulary: a `BackedEnum` unwrapped to its backing value, a `bool` coerced to `1`/`0`, an iterable mapped item by item, everything else `null`. Filament has no member because it has no comparison to make — its `selected` / `checked` attributes are written client-side by Alpine off the Livewire-hydrated model, where the port renders them in PHP ([why](forms/select.md#the-template-renders-the-selected-state-itself)). The nearest Filament code is the two-line `if ($state instanceof BackedEnum) { $state = $state->value; }` inside `Select::resolveOptionLabel()`, which is one arm of this in one method rather than a member to rename; naming it once is what keeps a label lookup and a `selected` attribute from disagreeing. |
| [`isMultiple()`](forms/checkbox-list.md#ismultiple-is-port-plumbing-with-no-filament-counterpart) | `Sylament\Forms\Components\CheckboxList` | A constant `true` declaring that this field always speaks a list, so the shared [`HasRelationship`](forms/checkbox-list.md#the-to-many-relationship-arm-serves-this-field-unchanged) arm can refuse a to-one association. Filament needs no member because it reads the same fact off a **type**: its `CheckboxList::getRelationship(): ?BelongsToMany` says "to-many" in the signature and its `Select` has a separate `isMultiple()` of its own, so nothing has to ask a checkbox list. The port serves both fields from one trait, which asks. It is internal in a way `Select`'s same-named method is not — there is no `multiple()` setter here, because there is nothing to choose. |
| [`ValidDate`](forms/date-comparison.md#the-date-comparison-family-builds-constraints-where-filament-builds-rule-strings) | `Sylament\Forms\Validation` | The constraint behind the date fields' validity check. Filament writes Laravel's `rule('date')`, a rule name with nothing behind it in Symfony: `Type('string')` says nothing about parseability and Symfony's own `DateTime` constraint demands one exact format, where a `datetime-local` control legally sends [several spellings](forms/date-time-picker.md#the-wire-format-uses-a-space-and-the-browser-answers-with-a-t) of the same instant. So the check had to become a class, and there is no Filament class to rename from. |
| [`DateComparison`](forms/date-comparison.md#the-date-comparison-family-builds-constraints-where-filament-builds-rule-strings) | `Sylament\Forms\Validation` | The constraint behind `after()` / `afterOrEqual()` / `before()` / `beforeOrEqual()` and the pickers' `minDate()` / `maxDate()`. | [`getTableGroupingColumn()`](tables/grouping.md#a-null-direction-is-not-ungrouped) | `Sylament\Tables\Concerns\CanGroupRecords` | The id half of the `<id>:<direction>` token, read back off the property. | [`getTableRecordGroupBoundaries()`](tables/grouping.md#the-group-boundaries-are-one-php-map-rather-than-loop-carried-template-state) | `Sylament\Tables\Concerns\CanGroupRecords` | Where each rendered record sits in its group — first, last, and how many rows into it — as one map keyed by record key. Filament has no member because it has no map: its Blade loop carries `$previousRecordGroupKey` / `$previousRecordGroupTitle` from row to row and compares as it goes. Naming the answer is what lets Unit assert it without rendering, and what gives the trailing-summary probe somewhere to fold into. |
| [`getGroupedTableSummaryQuery()`](tables/summarizer.md#the-per-group-figure-is-one-scoped-query-per-group-not-one-group-by) | `Sylament\Tables\Concerns\CanSummarizeRecords` | The all-table query scoped to one group, which is how a per-group summary row reads a figure. | [`Columns\Summarizers\Concerns\HasSelectAlias`](tables/summarizer.md#the-alias-trio-is-one-trait-behind-a-marker-interface-where-filament-copies-it-three-times) and its `Contracts\HasSelectAlias` marker | `Sylament\Tables\Columns\Summarizers` | The `selectAlias()` / `getSelectAlias()` / `getSelectedState()` trio Filament copies verbatim into `Sum`, `Average` and `Count`, shared here as one trait — and the interface the batch tests before pushing an alias onto a summarizer, since a trait member is not a type PHPStan can ask about off the base at level max. | [`Query\SummaryQuery`](tables/summarizer.md#every-summary-read-is-one-clone-with-the-order-reset-and-the-paging-cleared) — `readRow()`, `readDistinct()`, `qualifyAttribute()` | `Sylament\Tables\Query` | The read primitive every summary figure goes through: one clone with the order reset and the paging cleared, the select replaced, and a to-many join refused. Filament writes the equivalent inline in each summarizer as `$query->select(…)->get()` on an Eloquent builder — there is no class to rename, and the three Doctrine constraints it exists to enforce ([no stale `ORDER BY`](tables/summarizer.md#every-summary-read-is-one-clone-with-the-order-reset-and-the-paging-cleared), no `LIMIT` over an aggregate, no inflating join) have no Eloquent counterpart to state them at.
