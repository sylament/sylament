## What this is

Sylament is a Filament-inspired UI toolkit for Symfony, delivered as a monorepo of nine Symfony bundles under `packages/`: `actions`, `forms`, `infolists`, `notifications`, `panels`, `schemas`, `support`, `tables`, `widgets`. Package names mirror Filament's PHP packages and the same layered dependency idea applies (`support` is the base; `schemas` builds the component model; `forms`/`infolists`/`tables` build on `schemas`; `panels` composes everything). The project is early-stage: `support` and `schemas` are the most built-out — `schemas` and `forms` now map state onto Doctrine records, associations included — a `Relationship` value object naming one owner and one association is what the `AssociationReader` turns into a scoped query, a candidate query and owning-side writes, and `Identity\` beside it keys a record of **any** identifier width — ## Reference Filament's implementation

Two stances outrank everything in this section — read [`docs/principles.md`](docs/principles.md) first. In short: Filament's public API is preserved, but its *internals* have no claim on us when Symfony does it differently (§1), and anything Symfony's ecosystem already ships is adopted rather than rebuilt (§2).

This project is a deliberate Symfony port of Filament. Before designing or extending any component, trait, or API surface, **read how Filament does it first** — their decisions encode years of API ergonomics work and we want to inherit them unless we have a concrete reason to diverge (Symfony idiom, missing dependency, etc.).

Filament's source is installed at `vendor/filament/` (dev dep, never shipped). Useful entry points:
- `vendor/filament/schemas/src/Components/Component.php` — the base component analogous to our future `Sylament\Schemas\Components\Component`.
- `vendor/filament/schemas/src/Components/Concerns/` — single-purpose traits; we will mirror this directory by name as schemas grows.
- `vendor/filament/forms/src/Components/`, `vendor/filament/tables/src/`, etc. — per-bundle equivalents.

When porting, preserve trait names, method names, and the closure-evaluation parameter set (so users carrying Filament mental models stay productive). Translate Laravel idioms to Symfony equivalents (e.g. Eloquent → Doctrine, Livewire → UX LiveComponent, Blade → Twig, `Htmlable` → `Twig\Markup`) but keep the public API shape. The `Htmlable` translation is an escaping contract: wherever Filament types a human-text value as `string | Htmlable | Closure`, we type it `string|Markup|Closure` — plain strings are escaped by templates, `Markup` renders raw (Twig's escaper passes `Markup` instances through untouched, exactly as Blade does with `Htmlable`). When Filament puts a trait on the base class even though only some subclasses use it (e.g. `HasColumns`), assume the choice is for uniform fluent composition and follow suit unless you can articulate why the divergence is worth it.

Preserve Filament's API names by default — migrating users grep for them. Renaming is possible but narrowly gated: `docs/progress/renames.md` owns the criterion, the table of every rename made, and the systematic idiom/namespace translations that are *not* renames. Read it before renaming anything, and record the rename there in the same change.

Porting state lives in `docs/progress/` — read `docs/progress/README.md` first: it carries the rules (what earns a file of its own, how to keep the trail in sync) and the status vocabulary every table uses. Per-component state is `docs/progress/<package>/<component>.md`, a surface table over the component's features with per-row detail sections and divergences at the bottom (see `docs/progress/support/component.md` for a filled-in example). Keep these current in the same commit as the code they describe — stale entries are bugs.

## Monorepo wiring (read this before touching deps)

- **One root `vendor/`.** The repo root is a single Composer project. Every bundle is symlinked in via a Composer path repository (`"repositories": [{ "type": "path", "url": "packages/*" }]`) and required as `self.version`. Never run `composer install` inside a sub-package — there is only one lockfile and one vendor at the root. A stray `packages/*/vendor` or `packages/*/composer.lock` is leftover cruft; delete it. Lockfile policy (deliberate): the root `composer.lock` is **not** committed — this is a library monorepo, resolution floats within constraints and CI resolves fresh — while `pnpm-lock.yaml` **is** committed, because the pinned JS toolchain must reproduce the committed `assets/dist` byte-for-byte.
- **All dev dependencies live in the root `composer.json`.** Sub-package `composer.json` files carry production `require` only (their real inter-bundle dependencies). When a bundle needs a new dev tool, add it to the root.
- **Dependency policy**: `symfony/*` packages are pre-approved — add one to the root or a sub-package `require` whenever the work needs it, without asking first. That blanket approval was granted on 2026-08-10 and is the only *blanket* one; any other vendor still needs explicit sign-off before entering any manifest, and three such grants exist, all recorded as [carried decisions](docs/progress/roadmap.md#m3--forms-widening) on the roadmap: two made 2026-08-17 — SortableJS for the shared drag-and-drop control, and `league/flysystem` plus a scoped FilePond for the file upload — and, 2026-08-24, Cropper.js with FilePond's five image plugins for the image editor. The declaration rules are unchanged either way: each package declares what its own `src/` and `templates/` use, dev tools go to the root. So the flysystem grant lands as three different entries — `forms` **requires** `league/flysystem: ^3` because its `src/` writes through the operator, `support` only **suggests** it and `league/flysystem-bundle` (the guarded optional integration below), and `league/flysystem-bundle: ^3.7` is a root **dev** dependency, since the DI wiring that turns configuration into tagged storages is the consuming application's to install.
- **Assets are a separate pnpm workspace.** `pnpm-workspace.yaml` globs `packages/*/assets`. The other bundles join the workspace once they get one. PHP and JS are independent dependency graphs that meet only through Symfony AssetMapper.
- `pnpm-workspace.yaml` sets `hoistPattern: []` — transitive deps are NOT reachable by parent-walking. If you get "Module not found" in a workspace, add the dep explicitly to that workspace's `package.json`.
- **Working in a git worktree** (the default for agent-run implementation work): a worktree has no `vendor/` and no `node_modules`, and the root `composer.lock` is deliberately uncommitted — so each worktree needs its own `composer install` (a fresh floating resolution, which can pull newer dev tools than the main checkout has) and, if it touches assets, its own `pnpm install`. Both work; budget the setup time rather than avoiding worktrees. Pin the base at creation (`git worktree add <path> -b <lane-branch> <sha>`) — worktrees otherwise spawn from `main`, which may be behind an in-flight epic. Two env traps, both PHPStan: a stale `vendor/phpstan` can bake in a deleted worktree's absolute path (reinstall fixes it), and the `$TMPDIR` PHPStan cache is *shared* across worktrees, so clear `$TMPDIR/phpstan` and `$TMPDIR/cache/PHPStan` on internal errors. Keep lanes file-disjoint (progress-doc tables are the usual conflict magnet) and let one lane own the `assets/dist` rebuild at close-out.
- Each push to `main` (and each tag) is split out to per-package read-only repos under the `sylament` org by the `split-monorepo` job in `.github/workflows/ci.yml`; the split runs only after the `php` and `assets` gate jobs pass (the definition-of-done gates, plus a check that the committed `assets/dist` matches a fresh build). Keep each package self-contained so the split stays valid. Split-repo tests can't run standalone (the Pest bootstrap needs the root vendor) — accepted, since each package's `.gitattributes` export-ignores `/tests` from dist archives anyway.

## Core architecture

**Bundle base class.** Every bundle extends `Sylament\Support\SylamentBundle` (an `AbstractBundle`). Its `isAssetMapperAvailable()` guard is why asset-mapper is optional: each bundle's `prependExtension()` registers its `assets/dist` directory into the `framework.asset_mapper.paths` config under the alias `@sylament/<pkg>`, but only when AssetMapper is actually present. Services are wired in `loadExtension()` via the PHP DSL configurator (no XML/YAML service files). Consumer-facing settings are semantic config declared in `configure(DefinitionConfigurator)`. **`support` owns the `sylament` extension** — `protected string $extensionAlias = 'sylament'`, overriding the name `AbstractBundle` would otherwise derive (class name minus `Bundle`, underscored, i.e. `sylament_support`). That alias is for settings the whole toolkit shares and support's services back; `sylament.icons` (an alias→icon override map fed to `IconManager::register()`) and `sylament.colors` (a name→palette map fed to `ColorManager::register()`) are two of its four nodes — same `->call('register', [$config])` wiring, except that `colors` takes a `variablePrototype()` because its value is a union (a colour string to generate a palette from, or an explicit shade map) where a `scalarPrototype()` would reject the map arm. The other two are plain scalars read straight into a service definition rather than registered onto a manager: `sylament.default_filesystem_disk` (the flysystem storage a file component writes to when it names none) and `sylament.temporary_file_url_expiry_minutes` (integer ≥ 1, default 30 — how long a signed URL minted for a private file stays valid), both constructor arguments of `Filesystem\FilesystemRegistry` ([filesystem-registry.md](docs/progress/support/filesystem-registry.md)). Package-specific config keeps its derived `sylament_<pkg>` alias — a bundle cannot extend another bundle's config tree, so anything a higher package owns has to live under its own. Exactly one bundle may claim `sylament`, and nothing enforces it: `ContainerBuilder::registerExtension()` is a plain array assignment keyed by alias and `Kernel::prepareContainer()` loops without checking, so a second claimant replaces the first and the loser's `loadExtension()` never runs — surfacing much later as a missing service, never as a duplicate-alias error. The realistic claimant is our own: a **concrete** bundle named `SylamentBundle` would derive exactly `sylament`. Today's `SylamentBundle` is the abstract base and is never registered, so it cannot collide; if a real meta-bundle is ever wanted, it must set its own `$extensionAlias`. An Integration test pins support's alias so the choice cannot be silently "corrected" back to the derived name. Note the alias deliberately breaks Symfony's bundle-name convention — `Bundle::getContainerExtension()` throws a `LogicException` for exactly this mismatch, and it only passes because `AbstractBundle` overrides that method. **Any config node keyed by user-supplied strings needs `->normalizeKeys(false)`** — `ArrayNode::preNormalize()` rewrites any key containing a dash and no underscore, so `modal.close-button` silently becomes `modal.close_button` and matches nothing. It fails with no error at all, which is why `SylamentSupportBundleTest` pins it with a test that resolves the underscore form to null.

**Closure evaluation — the central pattern.** Almost every configurable value in the API can be either a literal or a closure, mirroring Filament. Two `support` pieces implement this:
- `Sylament\Support\Evaluation\Invoker::call()` reflects a callable's parameters and resolves each in order: explicit `$namedInjections` (by name), explicit `$typedInjections` (by class-string; `self`/`parent` hints are normalized against the declaring class; a `Closure` passed as a named/typed injection *value* is invoked with no arguments and its result injected — Laravel `value()` parity), the `$resolveParameter` callback (`fn (string $name, ?string $typeName)` returning a `ClosureParameter` wrapping the value, or `null` to skip), the DI container (only when `has()` knows the type), the declared default value, then `null` for optional/nullable parameters — otherwise it throws (naming the evaluating class when called through `evaluate()`). A variadic parameter still takes an explicit named/typed/resolver injection when one is supplied; only when none is does it get skipped (leaving `...$x = []`) rather than resolved from the container/default/`null` — so it never receives the spurious `null` Filament passes. There is no `app()->make()`-style auto-wiring of unbound classes (Symfony's container can't).
- `Sylament\Support\Concerns\EvaluatesClosures` is the trait classes use. `evaluate($value, $namedInjections, $typedInjections)` (Filament's parameter names) returns `$value` as-is unless it is a `Closure` instance (a literal string that happens to name a function — `'date'`, `'strtoupper'` — is a value, never invoked), otherwise calls it through `getInvoker()` — an `Invoker` injected by `#[Required]` setter, falling back to a container-less one built on first use, so a component created with `new` rather than through the container evaluates closures but resolves no services into them — passing a resolver that runs: `resolveDefaultClosureDependencyForEvaluationByName(string $name)` → `resolveDefaultClosureDependencyForEvaluationByType(string $type)` (both overridable, returning `ClosureParameter::make(...)` or `null` to skip) → the instance itself when the parameter is named `$evaluationIdentifier` or type-hints the instance's own class. The schemas base `Component` sets `evaluationIdentifier = 'component'` and `Schema` sets `'schema'`, so `fn ($component) => …` / `fn (Section $component) => …` / `fn ($schema) => …` receive the object being configured.

**Closure typing convention (PHPStan level max, consumer-safe).** Setters take native `Closure` unions with direct assignment and no param PHPDoc — Filament-exact: `public function heading(string|Markup|Closure|null $heading): static { $this->heading = $heading; }`. Never write an arity spec (`callable():T` / `Closure():T`) for a closure whose parameters the Invoker injects: PHPStan cannot express reflection-injected parameters, and a published arity-zero spec false-positives `fn (Section $component) => …` in every consumer's analysis. `evaluate()` carries the only generics: `@template T @param T|Closure $value @return T` — PHPStan infers T by subtracting `Closure` from the prop's union (`string|Closure|null` → `?string`), so props need no docblock beyond native types (array-shaped props keep bare-`Closure` docblocks, with entry types widened to include closure results where those differ, e.g. `HasColumns`). Closure/callable PHPDoc signature specs are not written anywhere — natives + prose carry the contract (a spec would only be truthful for callbacks invoked directly with fixed arguments, and even those go without).

**Static instance pattern.** For a service that must be reachable from a **static method or a free function**, where no injected property is in scope. That is the whole test, and it is why `Invoker` no longer uses it — `evaluate()` is an instance method, so a `#[Required]` setter reaches it. The mechanism:
- A class implements `Sylament\Support\DependencyInjection\Contracts\StaticInstance` and uses the `DependencyInjection\Concerns\HasStaticInstance` trait. `StaticInstance` is the codebase's only interface and carries no `Interface` suffix — `Contracts\` already says what it is, matching `Contracts\ScalableIcon` and `Contracts\InteractsWithActions`.
- `StaticInstancePass` (a compiler pass) auto-tags every service definition whose class implements the interface.
- `StaticInstanceRegistry` is constructed with `tagged_iterator(StaticInstance::class)` and, on `SylamentSupportBundle::boot()`, calls `setInstance($self)` on each tagged service so the static accessor works.
- Tests call `StaticInstanceRegistry::unsetStaticInstances()` in `tearDown` (see `packages/support/tests/TestCase.php`) so state doesn't leak between cases.
  `ComponentManager` and `ComponentResolver` use the pattern today, each pinned by a static call site: `Configurable::configureUsing()` and `Component::newInstance()`. Reach for it only when the call site is a static method or a free function — an instance method takes a `#[Required]` setter instead (`EvaluatesClosures`, schemas' `CanAccessProperties`), and the cost of that trade is that a `new`-built object gets a fallback dependency rather than the container's. Before accepting a free function as pinning, check whether it should be a free function at all: `IconManager` was a static instance only because the ported `generate_icon_html()` was one, and moving that body onto its sole caller `IconExtension` removed the need. Every function in `helpers.php` is now pure — keep it so. Unlike `ComponentManager`, `ComponentResolver`'s service definition is *not* `factory(ComponentResolver::resolve(...))` — it is a plain `set()` with `$components` defaulted to `null`, so only the container-built instance carries the locator; `resolve()` is purely the outside-DI fallback (see the Component model paragraph below).

**Global configuration.** `Sylament\Support\Configuration\ComponentManager` is the Filament `configureUsing()` port: `X::configureUsing($closure)` (via the `Configurable` trait) registers a class-keyed closure, and every `make()` runs `configure()`, which walks the class hierarchy root-first — calling `setUp()` at its declaring class's position, each class's registered closures after it, and `isImportant` closures last. `during:` scopes a registration to one closure's run; otherwise `configureUsing()` returns a removal closure. `ComponentManager::resolve()` returns the booted static instance or lazily creates one outside DI (the service is defined with `factory(ComponentManager::resolve(...))` so both are the same object); Unit suites unset it in a `tests/Pest.php` `afterEach` hook.

**Component model (today: in `support`).** Every `make()` factory goes through `Component::newInstance()`, which calls `ComponentResolver::resolve()->instantiate(static::class)`. `SylamentSupportBundle::build()` autoconfigures every `Component` subclass the application registers as a service with the `sylament.component` tag; `ComponentResolverPass` marks each tagged definition non-shared and collects them into a class-keyed `ServiceLocator`. A subclass the app registered this way is autowired and non-shared — its own constructor dependencies, including private services, are resolved on every `make()` call. Sylament registers its own components too: each bundle PSR-4-loads its `Components/` directory in `loadExtension()` with a glob that names only the component levels — a top-level `__DIR__ . '/Components/*.php'` everywhere except the two bundles whose components nest: `schemas` globs `__DIR__ . '/Components/{*,Tabs/*,Wizard/*}.php'` and `forms` `__DIR__ . '/Components/{*,Repeater/*,TextInput/Actions/*}.php'` — which keeps `Concerns/`, `Contracts/`, `StateCasts/` and `Utilities/` out without an exclude list — abstract bases come through as `container.excluded` stubs and are harmless. `Action`/`ActionGroup` are `set()` explicitly, since they live at `src/` root rather than under `Components/` — as are the prebuilt actions beside them: `CreateAction`/`EditAction`/`ViewAction`/`ReplicateAction`/`DeleteAction`, `BulkAction`/`BulkActionGroup`/`DeleteBulkAction`, and the six relationship actions `AttachAction`/`DetachAction`/`DetachBulkAction`/`AssociateAction`/`DissociateAction`/`DissociateBulkAction`. `forms` declares a **second** glob beside its component one — `->load(__NAMESPACE__ . '\\Validation\\', __DIR__ . '/Validation/*Validator.php')->autowire()->autoconfigure()` — because two of its constraint validators need a service: `ContainerConstraintValidatorFactory` resolves a `validatedBy()` through a locator and otherwise falls back to `new $class()`, which for a validator with a required dependency is an `ArgumentCountError` rather than a validation failure. The `*Validator.php` suffix is what keeps the constraints themselves — value objects, several with required constructor arguments — out of the glob, and `Validation/Concerns/` out with them. So `make()` normally returns a container-built, autowired, non-shared instance, and `#[Required]` setter injection works on a component. `new $class()` is the fallback for a class nobody registered — a user subclass that did not opt in — and there **a subclass declaring constructor dependencies must be a registered service**, or `make()` throws the ordinary missing-argument error. The measured cost of routing `make()` through the locator is 0.0002 ms per component (0.0009 → 0.0011 ms), so it is not worth avoiding. The abstract base is `Sylament\Support\Components\Component`, which composes `EvaluatesClosures` and `Configurable`. `Sylament\Support\Components\ViewComponent` extends it with Twig-backed rendering: `template()` / `templateData()` setters (each closure-evaluable), `getTemplate()` / `getTemplateData()`, and `render(Environment $twig)`. `Sylament\Support\Twig\Extension\ComponentExtension` exposes a `renderComponent(component)` Twig function backed by `ViewComponent::render()`. Attribute rendering in templates goes through `Sylament\Support\Twig\Extension\AttributeExtension`: `attrs(...sources)` is the `html_attr()` replacement backed by `ComponentAttributeBag` (later scalars win, class/style token lists append; class values take strings/conditional maps directly), and `classes()`/`styles()` build a token list and a declaration list for the one place a foreign bag renders attributes (ux-twig-component's `attributes.defaults()`). **That foreign bag appends `class` but *replaces* `style`** — `ComponentAttributes::defaults()` concatenates only `class`, `data-controller` and `data-action` — so a template emitting a `style` of its own (the inline colour palettes) merges by hand: `attributes.without('style').defaults({style: styles(ours, attributes.all.style ?? null)})`, ours first so the caller still wins per property. Handing `style:` straight to `defaults()` lets one caller attribute wipe the whole palette while `sy-color` stays on the element, which fails silently. **Build a conditional attribute set with `attrs()`, not a chain of `{% if %}` guards** — the bag already encodes what those guards spell out: `null` and `false` drop the attribute, `true` renders it, and every other scalar renders including `0`, so `rows: component.getRows` *is* `{% if getRows is not null %}`. **An `aria-*` key is the exception**: `ComponentAttributeBag::toScalarAttributes()` stringifies its booleans for Laravel parity, so `false` renders as `aria-x="false"` (and `true` as `aria-x="true"`) and only `null` drops it — an aria ternary must fall back to `null`, never `false`. Two things it does not do for you. An attribute guarded on **truthiness** rather than null needs `?: false`, or an empty-string placeholder renders as `placeholder=""`. And an attribute that must render **empty rather than vanish** needs `?? ''` — `TextInput`'s `value` is the live case, since `getState()` is null for an unset field and a missing `value` is not the same as `value=""` to idiomorph, which will not reset a user-typed value against an attribute that isn't there. `twig/html-extra` is not a dependency and its helpers are banned in templates (enforced by Twig-CS-Fixer's `ForbiddenFunctionRule`) — one attribute implementation, auto-registered by the bundle. Higher bundles subclass these (`schemas`' `Schema` and `Component` do today; the form fields will follow). Favor adding a focused `Concerns/Has*` trait over widening an existing class. Template context contract: `render()` passes `component` (the instance), then the `getExtraTemplateData()` class hook, then user `templateData()` (wins on key collision). Keep `getExtraTemplateData()` minimal — only values the template can't get from a single getter call (generated ids, fallback chains, cross-trait policy like Section's `collapsible`, child schemas needing constants or mutations); anything that is one getter is read in the template as `component.x`. It is the Twig-side port of Filament v5's `toEmbeddedHtml()` local-variable preamble — don't mirror plain getters into it. **A `LiveProp` on a host is de/hydrated through Symfony's `PropertyAccessor` (`LiveComponentHydrator::dehydrate()`), which prefers a same-named getter over the property, so `getFoo()` shadows raw `$foo` on the wire** — load-bearing where the getter mints the value (tables' `$tableHostId` fills lazily *because* the dehydration read is the minting read) and a defect where the client writes the prop back, since an element bound to a model the getter retyped is permanently dirty and re-fires its `onUpdated` hook on every request; bridge that second face with `dehydrateWith:` returning the value the element speaks, never by renaming a Filament getter ([both faces](docs/progress/tables/has-table.md#the-writable-props-dehydrate-in-their-elements-wire-vocabulary)).


**Colour.** A colour is a *palette name* (or an inline shade map), never a shade — the shade is chosen per palette, at render time, by a **contrast policy**. Four pieces, all in `support` except the per-package policies. `Sylament\Support\Colors\Color` is pure static data and maths: 26 palette constants, the oklch/rgb/hex conversions, `calculateContrastRatio()`, and `findShade()`, which walks a palette lightest-first (or darkest-first) and returns the first shade clearing a ratio. `Sylament\Support\Colors\ColorManager` is the registry — `DEFAULT_COLORS` merged with whatever `sylament.colors` and `register()` add, memoised on first `getColors()` — and it is also the emitter: `getComponentClasses(policy, name)` returns `['sy-color', 'sy-color-<name>', 'sy-text-color-700', …]` and `getComponentCustomStyles(policy, palette)` returns the inline `--sy-color-*` / `--sy-<slot>` declarations for an **array** colour. The policies live under `Colors\Components\` **per package** (support ships ten, schemas two, tables two) — filed by capability, *not* under `Twig\Components\`, which already means a class-backed renderable component — each implementing `Colors\Contracts\HasColor::getColorMap(array $color): array<string, int>` and expressing intent rather than a number (`->slot('text', surface: $color[50], fallback: 900)` is *"readable against this palette's shade 50"*). Delivery is `ColorExtension`: `colorAttributes(policyClassString, color)` returns `{class: [...], style: [...]}` to spread through `attrs()`, and `sylamentStyles()` emits a `<style>` block for registered palettes only. Six rules that are easy to get wrong. (1) **Never hardcode a shade in a stylesheet for a colour a user can set** — `@apply text-color-600` was a real shipped AA failure on four of six palettes; read a slot variable (`text-(--sy-text)`) and let the policy pick. (2) A policy is a **public** service, because `ColorManager` resolves it from the container by class-string and a private service is unreachable through `Container::get()`; every `Colors/Components/` glob a bundle declares carries `->public()`, and a package whose policies nest declares one glob per directory level (support ships three, tables two). (3) A policy returning `[]` is complete, not a stub — the two base classes are built before the map is consulted, so an empty map still swaps the palette and lets CSS fix the shade. (4) `HasDefaultGrayColor` means `gray` emits **nothing**, so the component's `:not(.sy-color)` branch paints it. (5) An **unknown** name emits the two base classes and no shade class, and there is no fallback palette — it renders uncoloured, on purpose. (6) A template emitting an inline palette must merge `style` by hand (`attributes.without('style').defaults({style: styles(ours, attributes.all.style ?? null)})`), per the `ComponentAttributes::defaults()` trap above. Full trail: [color.md](docs/progress/support/color.md), [color-manager.md](docs/progress/support/color-manager.md), [color-policies.md](docs/progress/support/color-policies.md), and [docs/styling.md](docs/styling.md) rules 5 and 6.

The split is load-bearing, not cosmetic — ux-twig-component's `ComponentTemplateFinder::findAnonymousComponentTemplate()` hardcodes the `components/` path segment, so anything under `templates/components/` is autodiscovered and callable as a tag whether or not it was written to be, and a PHP-rendered template invoked that way dies on the `component` variable only `ViewComponent::render()` supplies. That finder tries four paths in order (flat, `<Name>/index`, then both again under `@<Bundle>/components/`), which is why an anonymous component gets `<Name>/index.html.twig` for free; a **class**-backed component never searches at all — `ComponentFactory::metadataFor()` returns its compile-time config first — so it must always declare `template:` explicitly, and `name:` too, since name derivation matches the FQCN against the *application's* `twig_component.defaults`. Both halves are enforced by `packages/schemas/tests/Architecture/ComponentTemplateLocationTest.php`. **Order declarations by meaning, not alphabetically.** `{% props %}` groups by concern in the order the markup renders them — identity, state, header, content, footer, layout, behaviour, passthrough — with a blank line between groups; `{% set %}` follows the same shape, and where one derives from another, dependency order wins. This is what the `{% set %}` blocks already did (`FieldWrapper` orders its child schemas `above`/`below`/`before`/`after` by *position*, which alphabetising would scramble); only `{% props %}` was alphabetical, and it had already broken its own rule to keep `stickyHeader`/`stickyFooter` paired. Nothing enforces this — no formatter touches Twig — so it is judgment, and it only earns its keep on the long lists (`Section` 28 props, `Modal` 27); a two-prop component reads the same either way. Anonymous is the default: prefer it unless the component needs PHP, and prefer a component over `{% include %}` for anything a template renders — `{% props %}` states a contract an include's `with {}` only implies. A blank line separates a template's `{% set %}` preamble from the markup it computes for — every template does this, and it is the only visual break between "working out the values" and "emitting the output". **Attribute form on a `<twig:>` tag: `:name="expr"` for anything evaluated, bare `name="text"` only for a literal string.** So `:class="rootClasses"` and `:size="component.getSize ?? 'md'"`, but `color="gray"`. The trap is that "literal" means *string* literal — a bare `hasContentEl="false"` passes the **string** `"false"`, which is truthy, so booleans and numbers take the colon too (`:hasContentEl="false"`). This is a `<twig:>` rule only; a plain HTML element still interpolates with `{{ }}`.
**Invoke a component as `<twig:Sylament<Pkg>:<Name> />`, never `{% component %}`** — the HTML syntax is the house form, and there are no `{% component %}` calls left. It is not less capable: a computed attribute map spreads into the tag with `{{ ...map }}`, and slots are `<twig:block name="…">`. The one cost is that `<twig:>` has no `only` (the `{% component %}` tag does) — but only the **block** form pays it, and only for props declared without a default. A self-closing `<twig:X />` compiles to `{{ component('X', {…}) }}` and `ComponentRenderer::render()` passes `$context = []`, so it inherits nothing; the block form `<twig:X>…</twig:X>` compiles to `{% component %}` without `only` and does inherit. A prop declared **with** a default is immune either way — `PropsNode` resets it to that default whenever `__context` carries the name, and `__context` is the caller's context *minus the attributes the tag passed*, so an explicit `:name=` still wins — leaving the leak as exactly a **defaultless** prop, which the block form fills silently from a same-named caller variable while the self-closing form throws `<name> should be defined`. Give every prop a default unless you want that throw, and never rely on a variable the template doesn't declare. Two escapes from the tag form survive, both for the same reason — the name is only known at runtime, and a `<twig:>` tag name is a literal. `{% include %}` is one, in exactly one place: `ActionGroup/index.html.twig`, whose template name comes from `ActionGroup::getTriggerTemplate()`. The `component()` **function** is the other, in exactly two places: panels' `Document/index.html.twig` embeds the page's live component as `{{ component(componentName) }}`, the name being the FQCN-derived string `Page::getComponentName()` returns and `PageComponentPass` registers the page under; and schemas' `LiveComponent/index.html.twig`, the embed component's partial, which mounts an arbitrary registered live component by name or class-string — the mount must happen from a Twig frame, so the partial IS the call site ([live-component.md](docs/progress/schemas/live-component.md)). Three **class**-based components ship today, each because it needs PHP a template cannot reach: `actions`' [`Modals`](packages/actions/src/Twig/Components/Modals.php) must resolve its host live component by walking ux-twig-component's `ComponentStack` — inside a Twig component `this` is that component, not the host, so no template-scope approach works at arbitrary nesting depth (reasoned out in `docs/progress/actions/has-actions.md`) — `notifications`' [`Notifications`](packages/notifications/src/Twig/Components/Notifications.php) needs the injected `SessionNotifications` to drain the flash bag on a page load (`docs/progress/notifications/notifications.md`), and `panels`' [`GlobalSearch`](packages/panels/src/Twig/Components/GlobalSearch.php) is the topbar search field, holding the searched term as a `LiveProp` and answering it through the panel's search provider (`docs/progress/panels/global-search.md`). The third one is also the first `#[AsLiveComponent]` in `packages/*/src` — panels' pages are live too, but a compiler pass registers them rather than the attribute — and being live forces one thing a plain class component never faces: a live request goes to ux-live-component's own route, which carries no `_sylament_panel` route default, so the component keeps the panel id in a second `LiveProp` and stamps it back onto the request from a `#[PostHydrate]` hook. Without it the provider and every `Resource::getUrl()` underneath would silently answer for the **default** panel. A class component is a container service, so its bundle registers and `->autowire()->autoconfigure()`s it in `loadExtension()` — one line, no argument wiring — all three bundles do it with the same `->load(__NAMESPACE__ . '\\Twig\\Components\\', __DIR__ . '/Twig/Components/')` directory glob. Where a dependency has no class alias and autowiring cannot see it, the service id goes on the constructor parameter as `#[Autowire(service: 'ux.twig_component.component_stack')]`, not into the bundle's `args()`; keeping it on the class means adding a component never means editing the bundle beyond that one line. **Dependency declaration.** Each package declares what its own `src/` and `templates/` need, *even when a sibling already pulls it in* — every package requires `sylament/support`, but the CI split publishes each one standalone, so inheriting through a sibling is how a split repo silently breaks (`actions` fatally `use`d `ComponentToolsTrait` while only `schemas` declared `symfony/ux-live-component`). Two things count as needing it: a PHP symbol imported by `src/` (`Modals` type-hints `AsTwigComponent`/`ComponentStack`), or a Twig extension a shipped template cannot **parse** without (`{% props %}` in support's and forms' component templates). That test is about *unconditional* use — an import some code path always reaches is a `require`. The column catalog put three on `tables` at once: `symfony/html-sanitizer` and `symfony/validator`, both imported unconditionally by a `#[Required]` setter (`CanFormatState`'s and `CanBeValidated`'s), and **`ext-intl`**, which `TextColumn`'s `money()`/`numeric()` reach through `NumberFormatter` — an extension counts under the same test, and Filament declaring that one on `filament/support` rather than on `filament/tables` is precisely the inherit-through-a-sibling shape the split publishes away, so it is declared where the call is ([tables-bundle.md](docs/progress/tables/tables-bundle.md#the-manifest-grew-three-requires-and-one-suggest-for-the-column-catalog)). A **guarded optional integration** is the exception: code that is dead without the package — a branch gated on `instanceof`/`interface_exists`, or a service definition the package itself never instantiates — so the missing symbol is never resolved, takes a composer `suggest` plus the guard instead. `support` already ships one — `isAssetMapperAvailable()` around each bundle's `prependExtension()` hook — `actions`' table-context resolution is the second: `HasActions::resolveActions()` branches on `$this instanceof Sylament\Tables\Contracts\InteractsWithTable`, and `sylament/tables` is only suggested. Support's `Filesystem\FilesystemRegistry` is the third, and the guard is structural rather than a branch: it imports `League\Flysystem\FilesystemOperator` in `src/`, but nothing inside support ever constructs that service, so without flysystem the definition is simply never instantiated and the symbol never resolved — `league/flysystem` and `league/flysystem-bundle` stay `suggest`s while `sylament/forms`, whose `src/` does the writing, `require`s the library ([filesystem-registry.md](docs/progress/support/filesystem-registry.md#leagueflysystem-is-suggested-rather-than-required)). Tables' `league/commonmark` is the fourth and the plainest: `TextColumn::markdown()` is opt-in, the conversion sits behind `class_exists(GithubFlavoredMarkdownConverter::class)`, and the *else* branch is a `LogicException` naming the package rather than a fall-through to raw text — a guarded optional must fail loudly at the point of use, never degrade silently ([text-column.md](docs/progress/tables/text-column.md#markdown-throws-for-the-package-it-suggests-rather-than-falling-through)). The softer link costs the composer-level check, so pin each one with a test instead: a renamed or moved contract dead-ends the branch in silence, and tables' `RecordActionsResolutionTest` is what turns that into a failure, as `SylamentSupportBundleTest` — booting the real `FlysystemBundle` over two `local` storages — is for the tag the registry collects, and as `CanFormatStateTest` reading the `class_exists()` guard site is for the commonmark one, whose absent-library branch no install that has the library can reach. A **return type** is what forces the opposite call: `actions` requires `sylament/forms`, because `AttachAction::getRecordSelect()` and `AssociateAction`'s build and return a forms `Select` unconditionally, so there is no branch a guard could stand in front of — and with `forms` requiring `actions` back, that is the monorepo's second declared cycle beside `actions` ↔ `schemas`, exactly as Filament's own manifests have it (`sylament/tables` stays a `suggest` either way). Actions' Unit tests do build that `Select`, but the monorepo resolves every package out of one root `vendor/`, so the class autoloads whether or not actions' manifest names it and dropping the line would fail nothing here — only the split repo: [`ManifestTest`](packages/actions/tests/Architecture/ManifestTest.php) reads `composer.json` instead. Conversely, never push a dependency down into `support` that support itself doesn't use — it references `Symfony\UX\LiveComponent` nowhere, so that stays on `actions`/`schemas`/`forms`; `symfony/string` it **does** require, from M4 · 2 on and today for two consumers — `get_record_label()`'s `u()->kebab()` and `plural()`'s `EnglishInflector` ([helpers.md](docs/progress/support/helpers.md#get_record_label-is-a-rename-and-it-is-what-put-symfonystring-in-supports-manifest)). The two placeholder bundles (`infolists`, `widgets`) import only `SylamentBundle`, so `sylament/support` alone is complete for them; this rule adds nothing to a package that uses nothing.
Nine deliberate omissions, so their absence reads as a decision rather than an oversight: **`twig/twig`** is not declared by `actions`/`forms`/`notifications`/`panels`/`schemas`/`tables` despite direct `Twig\Markup` use — and, in all but `forms`, `Twig\Environment` too, joined variously by an extension or an error class (`actions`/`schemas`/`tables` import `AbstractExtension` and `TwigFunction`, `panels` imports `Error\RuntimeError`, `notifications` neither) (support declares it and Twig cannot leave the graph); **`symfony/type-info`** is not declared by `schemas` despite `State\RecordTypeReader` importing four of its symbols directly (`Type`, `Type\CollectionType`, `Type\NullableType`, `Type\ObjectType`) — same grounds as `twig/twig`, since `symfony/property-info`, which schemas *does* declare, hard-requires it (`symfony/type-info: ^7.4.7|^8.0.7`), so it cannot leave the graph; **`doctrine/dbal`** is not declared by `tables`, `schemas`, `forms` or `actions` despite `schemas`' `Query\SearchConstraint` importing `PostgreSQLPlatform` and its `Identity\` seam importing seven more — `Types\Type`, `Types\Types`, `Types\ConversionException`, `Platforms\AbstractPlatform`, `ParameterType` and `ArrayParameterType`, which is what typing a decoded key by its field's own DBAL type costs, and, since M7 · 5b, `Query\QueryBuilder`, the builder `IdentifierConstraint::inColumns()` binds on — `tables`' `Query\AggregateQuery` importing `ParameterType` and `ArrayParameterType`, and `actions`' `Concerns\CanUseDatabaseTransactions` importing `Connection` to wrap a mounted action in a transaction, all in `src/`, and the `tables`/`schemas`/`forms` Doctrine test rigs importing `DriverManager` — same grounds again, since `doctrine/orm`, which all four *do* declare (`^3.6`), hard-requires it (`doctrine/dbal: ^3.8.2 || ^4`), and every one of those symbols carries the same name across that whole range (the ORM's own `src/` imports the two parameter-type symbols unconditionally, so they cannot be absent from either major version, `Connection` is the declared return type of `EntityManagerInterface::getConnection()`, so an ORM that resolves at all brings it, and `Query\QueryBuilder` is what that `Connection::createQueryBuilder()` returns on both majors). A carried **name** is all that guarantee buys, and for the two parameter-type symbols that is narrower than it reads: `ParameterType` and `ArrayParameterType` are final classes of int constants on DBAL 3 and native enums on DBAL 4, so they may be used as **values** only — a `match` subject, a `setParameter()` argument, a constant read — never as a declared parameter, return or property type, and never as a positive `instanceof` (`AggregateQuery`'s negative guard is a value test and stays). A declared `: ParameterType` is a `TypeError` on every DBAL 3 application and no gate here can see it, since only DBAL 4 is installed, so [`DbalParameterTypeDeclarationTest`](packages/schemas/tests/Architecture/DbalParameterTypeDeclarationTest.php) is the pin that stands in for the composer-level check; **`doctrine/persistence`** is not declared by `actions` despite `Concerns\CanUseDatabaseTransactions` importing `Doctrine\Persistence\ManagerRegistry` in `src/` — how `DeleteAction` reaches the entity manager of an arbitrary record's class — and, since M7 · 3, `Action` importing `Doctrine\Persistence\ObjectManager` beside it to ask whether one scalar field is a record's whole identity — same grounds one package over, since `doctrine/orm`, which actions *does* declare (`^3.6`), hard-requires it (`doctrine/persistence: ^3.3.1 || ^4`) and both interfaces carry those names across both majors; **`doctrine/collections`** is not declared by `actions` or `tables` despite `actions`' `Replication\RecordReplicator` importing **and instantiating** `Doctrine\Common\Collections\ArrayCollection` in `src/` (every collection-valued association on a replica starts as a fresh one) and `tables`' `Columns\Concerns\HasCellState` importing `Collection` to `instanceof` a loaded association — same grounds as dbal and persistence, since `doctrine/orm`, which both *do* declare (`^3.6`), hard-requires it (`doctrine/collections: ^2.2`) and both symbols carry those names across that range. The two uses are not equally exposed: tables' is an `instanceof`, which PHP never autoloads for, so it is guarded by construction; actions' `new ArrayCollection()` is not, so an ORM-less `sylament/actions` fatals there. It stays undeclared rather than earning a `require` because `doctrine/orm` is already an actions `require` and cannot leave the graph — but this is the omission to declare first if that ever stops being true. **`psr/container`** is not declared by `panels` despite `Controllers\PageController` importing `Psr\Container\ContainerInterface` directly to type the page locator — same grounds a third time, since `sylament/support`, which panels *does* declare, hard-requires `symfony/service-contracts` (`^3.6`), which hard-requires `psr/container` (`^1.1|^2.0`), and the interface carries that name across both majors; **`symfony/config`** is not declared by `panels` despite `Routing\PanelRouteLoader` importing `Symfony\Component\Config\Resource\FileResource` to make the loader's routes recompile when a page or provider class changes — same grounds again, since `symfony/framework-bundle` hard-requires it (`^7.4.4|^8.0.4`) and nothing that ships a `RouteLoaderInterface` can be running without one; and **`symfony/dependency-injection` / `symfony/http-kernel` / `symfony/framework-bundle`** are declared nowhere despite every bundle extending `AbstractBundle` and wiring services, and despite `panels` importing `Symfony\Bundle\FrameworkBundle\Routing\RouteLoaderInterface` in `src/Routing/PanelRouteLoader.php` — the whole trio is treated as ambient, since framework-bundle is what a Symfony application *is* and it drags the other two in. That one is the weakest of the omissions, because it is a first-party import rather than a transitive guarantee: a split `sylament/panels` consumed outside a FrameworkBundle application fatals on the missing interface. It stays ambient because a panel is a full-application surface that cannot be assembled without framework-bundle anyway; declare it the moment panels ships something usable without one. And **`league/flysystem`** is not declared by `tables` despite `Columns\ImageColumn` importing `FilesystemOperator` and `UnableToCheckFileExistence` in `src/` — same grounds as dbal, since `sylament/forms`, which tables *does* require, hard-requires it (`league/flysystem: ^3`) and both symbols carry those names across that range; the imports are structurally guarded besides (only the disk-path arm reaches them, and it runs behind a registry `get()` that cannot succeed without flysystem), so a URL-state `ImageColumn` works with no flysystem anywhere, which is the [roadmap's "plain URLs without it"](docs/progress/tables/image-column.md). Revisit any of them only if a split package is ever consumed without its host (framework-bundle for the last trio and for config, property-info for type-info, orm for dbal, persistence and collections, support for psr/container, forms for flysystem).

## Conventions

- PHP: `declare(strict_types=1)` everywhere; PHPStan **level max** must stay green (only `trait.unused` is globally ignored; `reportUnmatchedIgnoredErrors` is on, so stale ignores fail the run — no baseline file exists). **Shipped source carries no inline `@phpstan-ignore`**, enforced by schemas' `StaticAnalysisSuppressionTest`: an inline ignore hides a real defect at the one place a reader is least likely to question it, so fix the cause instead — an unguarded nullable wants a throw, the way [`BelongsToSchemaComponent::getSchemaComponentOrFail()`](packages/actions/src/Concerns/BelongsToSchemaComponent.php) replaced the only three the codebase had. An error that genuinely cannot be fixed belongs in a baseline file, where it is counted and reviewable. PSR-4 namespace `Sylament\<Bundle>\` → `packages/<bundle>/src/`, tests `Sylament\<Bundle>\Tests\` → `packages/<bundle>/tests/`. Tests are Pest. Formatting is PHP-CS-Fixer + Rector — run `composer format`, don't hand-format.
- Helper functions: `Sylament\Support`-namespaced functions in `packages/support/src/helpers.php` (composer `files` autoload; import with `use function`). Ten ship today: `blank()`, `filled()`, `wrap()` (Laravel's `Arr::wrap`, including its `null` → `[]` arm; generically typed so element narrowing survives level max), `only()` and `except()` (Laravel's `Arr::only`/`Arr::except`, one `array_intersect_key()`/`array_diff_key()` over `array_flip($keys)` each), `get_record_label()` (Filament's `get_model_label()` under [the record vocabulary](docs/progress/renames.md#the-model-vocabulary-collapses-onto-record): a class-string's basename kebab-cased with the dashes spaced, and the first of the two reasons support requires `symfony/string`), `plural()` (Laravel's `Str::plural`, over `symfony/string`'s `EnglishInflector` and taking its last candidate: the **last word** of a phrase is inflected and the rest left alone, so `blog post` → `blog posts` — the second consumer that keeps `symfony/string` in support's manifest, and it drops Filament's `locale_has_pluralization()` branch, i18n being parked), `sanitize_url()` (Filament's `Str::sanitizeUrl` macro: the string back unchanged, or `null` when it is blank, carries a raw or entity- or percent-obfuscated control character, or names a scheme outside the allow-list — a relative URL has no scheme and passes), `sanitize_css_color()` (its `Str::sanitizeCssColor` sibling, landing here for the same reason: four hex widths, a bare keyword, and ten functional notations with `( ) ; : " '` forbidden inside the parentheses, else `null` — `ColorColumn`'s swatch is the caller, and it is **not** `ColorManager::sanitizeCssColor()`, which asks a different question and answers `''`), and `diff_for_humans()` (Carbon's `diffForHumans()` at its `$parts = 1` default, ported rather than depended on: the first non-zero unit of `year → month → week → day → hour → minute → second`, pluralised in English, with `$now` passed in so the function stays pure — `TextColumn::since()` is the caller). That list is the first stop **before writing any Laravel-helper-shaped mechanics**: when the Filament original leans on a Laravel helper, use the existing port; for a helper with no port yet, either add it here (pure only, its [helpers.md](docs/progress/support/helpers.md) row in the same commit) or reach the mapped Symfony mechanism where principles §2 sanctions one (`data_get`/`Arr::get` → `State\PropertyAccessor`) — never inline the helper's body at a call site. The `*On()` methods shipped a hand-rolled `is_array` ternary while `wrap()` sat five call sites away; that miss is what this sentence exists to prevent. `filled()` / `blank()` mirror Laravel's, except `Twig\Markup` is special-cased to text semantics: it is `Countable` (counts its characters), so Laravel's count-first order would call a whitespace-only `Markup` filled, while Laravel's `HtmlString` isn't `Countable`. Other `Countable+Stringable` objects (Doctrine collections) keep Laravel's count semantics. Two further deliberate deltas: `blank()` trims with `mb_trim`, so NBSP/em-space-only strings count as blank (Laravel's byte `trim` doesn't); and Laravel's `instanceof Model → filled` short-circuit has no Doctrine equivalent here, so a `Countable`-empty entity reports blank. Future Filament helper ports (`is_slot_empty`, …) go in this file **only if they are pure**. Every function here is today, and that is load-bearing: a helper needing a service can only reach one globally, which is precisely what made `IconManager` a static instance until `generate_icon_html()` moved onto `IconExtension`. Filament reaches a facade from several of its helpers (`get_component_color_classes()` will); port those onto the service or extension that owns the dependency, not here. **A second helpers file exists**: `Sylament\Forms`-namespaced functions in `packages/forms/src/helpers.php` (its own `files` autoload), mirroring Filament's forms helpers — `array_move_before()` and `array_move_after()` ship today (see [repeater.md](docs/progress/forms/repeater.md#the-move-helpers-correct-two-vendor-edge-defects)). The placement rule is by source: a *Laravel* helper's port lives in support, a *Filament-forms* helper's port in forms; the pure-only rule and the row-in-the-same-commit rule apply to both files. After editing a sub-package `composer.json`, run `composer update sylament/<pkg>` — plain `dump-autoload` reads the stale lock metadata for path packages, and run it **in each checkout separately**: features gated on Composer runtime metadata (`ContainerBuilder::willBeAvailable()` — the `sanitize_html` filter's auto-enable is one) silently stay off in a sibling checkout whose `installed.json` predates the manifest change.
- Concerns and contracts sit **one directory per object tier**, placed by *who uses* them rather than by what they do. `src/Components/Concerns/` holds traits for the nested-component tier; `src/Concerns/` holds traits for the package's own root object, plus host traits and general plumbing. So `schemas` has both — `Schema` is the root object and components nest inside it — while `actions` has only the root one, because `Action`/`ActionGroup` *are* actions' `Schema` rather than a nested tier, so all 42 of their traits are root-class traits and belong there (`HasActions` sits there too, as the trait a host composes). `support` applies the same test with one tier: everything a component composes is under `Components/Concerns/` — including `Configurable`, whose only consumer is `Component` — leaving two at root: `EvaluatesClosures`, a deliberate hold rather than a category (Filament's other two direct importers of it are `ColorManager` and `TimezoneManager`, plain classes, so it moves down only once colors prove otherwise — see [renames.md](docs/progress/renames.md#namespace-segments)), and `HasDefaultDataFormattingSettings`, the eight toolkit-wide date, money and number defaults, which is at root because what composes it is a **root object** rather than a component — `Tables\Table` today, `Schema` when M5 gives it a reader, exactly where Filament files it ([has-default-data-formatting-settings.md](docs/progress/support/has-default-data-formatting-settings.md)). `forms` has only `Components/Concerns/`. A trait a component uses at all lives under `Components/`, whether or not the root object uses it too — schemas' `CanAccessProperties`, `HasColumns` and `HasGap` are shared with `Schema` and still sit there. Root `Concerns/` is for traits the root object or a host uses **and components do not**: schemas keeps ten (`CanBeDisabled`, `CanBeInline`, `HasComponents`, `HasHeadings`, `HasKey`, `HasState`, …) plus the host trait `HasSchemas`. Read that list by **import**, never by the bare `use X;` in a class body — four of those ten share a name with a different trait in `Components/Concerns/`, so `use HasState;` means one thing in `Schema` and another in `Component`, and grepping the short form silently conflates them. Contracts follow the same line: one the **host** implements is root (`InteractsWithActions`, `InteractsWithSchemas`), one a **component** implements is `Components/Contracts/` (`CanConcealComponents`). A contract **neither** tier implements takes the engine's line instead, filed under the capability directory that consults it — schemas' `Validation\Contracts\ImplicitConstraint` is a marker a consumer puts on a Symfony `Constraint`, so it sits beside `Validation\PresenceGate` rather than at either root. The cost is inherited and accepted: the same trait name exists in both tiers — four in schemas today, nine at Filament parity — so check the namespace before assuming which `HasState` you have. Do not regroup by feature (`Concerns/State/`, `Concerns/Layout/`): Filament sub-groups no `Concerns/` directory anywhere and ships 50 flat in `actions`, so a feature layout would break the namespace mapping migrating users rely on and force a placement judgment on every trait still to port. Revisit only at parity, when the categories could be read off the finished set instead of guessed. The **engine** a trait delegates to is filed by capability at `src/` level, never under `Concerns/` with its trait: `EvaluatesClosures` → `Evaluation/Invoker`, `Configurable` → `Configuration/ComponentManager`. Never beside the class it operates on — Filament files `ComponentManager` under `Components/` and it is not a component, which is what forced an `exclude()` on the `Components/*.php` service glob. That glob registers component classes; anything else at the top of that directory is misplaced, and a second definition of a `StaticInstance` class is not a harmless duplicate (the registry `setInstance()`s both).
- Test layout (canonical, lived out in `support` and `schemas`): each bundle's `tests/` is split into buckets — `Unit/` for tests with no kernel boot (pure logic, compiler passes against a hand-built `ContainerBuilder`, trait behavior with fixture classes), `Integration/` for tests that boot the kernel or hit the container, plus an optional `Architecture/` bucket for repo-convention guard tests that scan files rather than exercise a SUT (e.g. schemas' `ComponentTemplateLocationTest`; no kernel, Pest default base). Inside `Unit/` and `Integration/`, **mirror the `src/` tree exactly**: `src/DependencyInjection/Compiler/StaticInstancePass.php` → `tests/Unit/DependencyInjection/Compiler/StaticInstancePassTest.php`, `src/SylamentSupportBundle.php` → `tests/Integration/SylamentSupportBundleTest.php`. `tests/Pest.php` attaches `TestCase` (the `KernelTestCase` subclass) only to `Integration/`; Unit tests use Pest's default base, and the Unit blocks in every `tests/Pest.php` unset the three static instances after each test — don't re-add per-file hooks. Test file names match the SUT (`FooTest.php` for `Foo.php`). Support's shipped Twig components are render-tested from **higher packages'** Integration suites, because support's own fixture Kernel registers no TwigComponentBundle/StimulusBundle — six do: `actions`, `forms`, `schemas`, `notifications`, `tables` and `panels`. Coverage splits by which package first needed the component, so it is **not** all in one place: `actions` renders Badge, Button, Link, DropdownItem, Dropdown, Modal, Section and IconButton; `forms` renders InputWrapper directly (its five text-like control templates are the consumers, and `panels` renders it through the resource pages' TextInputs; `tables` renders it **directly** too, since `TextInputColumn` and `SelectColumn` put their controls inside it — so this one component has two first-class homes and a change to it must be run against both suites), IconButton (the affix actions inside it and the repeater's handle/collapse buttons) and Tabs/TabsItem (its `ConcealmentTest` builds a `required` field inside a Tab); `schemas` renders Icon, IconButton, Fieldset, Section, Tabs, TabsItem, LoadingIndicator, Badge, Dropdown and DropdownItem (the last three through `TabsRenderTest`, on static tab badges and the `scrollable(false)` overflow dropdown); `notifications` renders IconButton, Link and Dropdown; `tables` renders Badge, Button, Link, Icon, IconButton, Dropdown, Pagination and — as of the column catalog — InputWrapper directly, plus support's code-less `.sy-checkbox` skin (`CheckboxColumn` emits it beside the selection column that already did), plus DropdownItem and Modal indirectly — a grouped action renders actions' `Grouped` template inside support's Dropdown, and every action-mounting table fixture template mounts `<twig:SylamentActions:Modals />`, so a mounted action's confirmation modal renders here too; `panels` renders Icon, Badge and Button (the first two through its sidebar templates, Button through the create/edit page save buttons) plus Breadcrumbs (the only suite that renders it at all — the resource pages are its sole consumer), Link and Pagination, and Modal and IconButton once an action is mounted — those four ride in through the resource list page, which renders tables' `Table` partial and the record actions inside it, so that partial's other support pulls (Dropdown, and Badge again) land here too the moment a fixture resource declares filters. So `composer test:support` alone doesn't exercise those templates, and a change to one can only be verified by running the suite that renders it — check both lists rather than assuming, since a plan that took schemas to own all of it broke eleven actions tests. Deliberate (docblock-noted there), revisit only if support grows its own Twig-component test kernel. The other two bundles — `infolists`, `widgets` — currently ship a placeholder `Feature/ExampleTest.php` — adopt the Unit/Integration split as real tests land, don't entrench `Feature/` (`panels` did exactly that when its first real tests landed).
- Fixture layout: `tests/Fixtures/` mirrors `src/` for per-test fixture classes (e.g. fixtures supporting `src/DependencyInjection/` tests live in `tests/Fixtures/DependencyInjection/`). Global test-app infrastructure (the `Kernel`, fixture service-config files) stays at the root of `tests/Fixtures/`. Don't dump everything flat — put each fixture next to the subsystem it exercises so it's findable as the suite grows.
- Test Kernel wiring: the test `Kernel` PSR-4-loads everything under `tests/Fixtures/` recursively with `autowire + autoconfigure` defaults (excluding `Kernel.php` itself). Adding a new fixture means dropping a class in the right `Fixtures/` subfolder — never edit the Kernel to register individual fixture services. Services stay private by default; `KernelTestCase::getContainer()` returns the `test.service_container` which exposes privates to tests, so you rarely need anything public. When a fixture genuinely must be public in the real container, opt in with `#[Autoconfigure(public: true)]` on the fixture class itself — never widen the Kernel defaults. If a fixture needs special construction, write a small config (e.g. `Fixtures/services_special.php`) and `import()` it from the Kernel rather than hand-wiring inline.
- Pest tests: inside `it()` / `test()` closures, reach static `KernelTestCase` helpers through `$this::` (e.g. `$this::getContainer()`, `$this::bootKernel()`) — never `static::` or `self::`. Pest binds `$this` to the configured `TestCase`, so `$this::foo()` resolves to that class's static method; `static::foo()` resolves against the anonymous closure scope and is wrong.
- Pest tests: don't call `bootKernel()` explicitly — `KernelTestCase::getContainer()` auto-boots when no kernel is booted. Just call `$this::getContainer()->get(...)` directly. Only boot explicitly when you need to pass options (`$this::bootKernel(['environment' => 'foo'])`) or grab the kernel object itself.
- TS: strict mode, `target` ES2022, ESM, bundler resolution (`tsconfig.base.json`). Biome enforces `useImportType`, `useConst`, and bans `any` and non-null assertions (`!`) as errors. Relative imports must carry the compiled `.js` extension (`useImportExtensions` with a ts→js mapping): the default per-file build runs without `--bundle`, so specifiers ship verbatim to the browser and an extensionless import would pass `tsc` but 404 at runtime. Stimulus is a peer dep pinned to `^3` via workspace overrides. `@floating-ui/dom` is a regular dependency bundled into `dist` via the `BUNDLED_ENTRIES` table in `scripts/build-js.mjs`, never resolved by consumers; so is `sortablejs`, bundled into support's `sortable` controller — a second copy beside forms' select engine, pinned to one version by the workspace override. It is no longer the only shipped third-party asset: `@fontsource-variable/inter` ships too, but by a different route — `assets/scripts/copy-fonts.mjs` (beside `scope-preflight.mjs`, and invoked the same way) copies the latin woff2 and the package's LICENSE into `dist/styles/fonts/`, because `.gitattributes` export-ignores `assets/src` and `assets/scripts` from the split repo, so only what lands in `dist` is published. It resolves sources through `require.resolve`, which throws on a missing package, since AssetMapper's `CssAssetUrlCompiler` passes an unresolvable `url()` through behind a log warning and the failure would otherwise surface only as a browser 404. Forms bundles two more third-party libraries — `@floating-ui/dom` (again; support's dropdown has its own copy) and `sortablejs` (again; support's sortable control has its own) — into its `select` controller, and ten more into its `file-upload` controller: `filepond` with `filepond-plugin-file-validate-size`, `filepond-plugin-file-validate-type`, `filepond-plugin-image-preview`, `filepond-plugin-image-crop`, `filepond-plugin-image-edit`, `filepond-plugin-image-exif-orientation`, `filepond-plugin-image-resize` and `filepond-plugin-image-transform`, plus `cropperjs`. All twelve are MIT, served by the banner as support's Floating UI is, and eleven ship types of their own; `sortablejs` does not, so `@types/sortablejs` is a dev dependency of that workspace. `@sylament/schemas` bundles nothing — its `BUNDLED_ENTRIES` table is empty and every controller and util builds per-file — and it is the one workspace another workspace imports from, through an `exports` map (`"./utils/*.js": "./src/utils/*.ts"`) that hands forms' two bundled controllers the **TypeScript source** to inline: `utils/schema_component_method.ts` for both, and `utils/live_host.ts` for `file-upload`.
- CSS: semantic `sy-<pkg code>-*` classes only in Twig (never utilities — template scanning is off), e.g. `sy-fo-input`, `sy-sc-grid`; every component template root also carries the bare `sy` marker class; `@apply` authoring in `packages/<pkg>/assets/src/styles/components/<name>.css`; dynamic per-instance values via inline `--sy-*` CSS variables; colors through the `--sy-*` runtime tokens; Tailwind preflight is never shipped page-wide — `support`'s build generates a `.sy`-scoped copy from the installed Tailwind (`assets/scripts/scope-preflight.mjs`). The one `@font-face` the toolkit ships (Inter Variable, latin) lives in `support`'s `assets/src/styles/fonts.css` and **must stay a sibling of `index.css`** — its relative `url()` resolves only because source and output sit at the same depth (styling.md rule 10). A class a **bundled JS library** emits is never selected bare at top level — the stylesheet is page-wide, so `.sortable-ghost` would style a host app's own widget of the same name: reach it under a `sy-` class handed to the library through its own class settings, or qualified by the `sy-` class of the element the library stamps its class onto, and never re-emit it from Twig; a **vendor base stylesheet** we redistribute is rewritten under the component's class by the build rather than imported bare (styling.md rule 11 — one live case per branch: support's `sy-sortable-ghost`, handed to SortableJS through `ghostClass` and styled in `components/sortable.css`; forms' `file-upload.css`, nesting every `filepond--*` override under `.sy-fo-file-upload`; and FilePond's own stylesheets, regenerated scoped and keyframe-renamed by `scope-vendor-css.mjs`). Cropper.js's stylesheet is the second generated vendor sheet: `scope-vendor-css.mjs` rewrites `cropperjs/dist/cropper.css` as forms' gitignored `cropper.generated.css`, every rule scoped under `.sy-fo-file-upload-editor` — the dialog's class rather than the field's, since Cropper's DOM only ever lives inside it. Full contract: `docs/styling.md`.
- Comments: the test is whether the comment states something **the code cannot**. Type-carrying PHPDoc (`@param`, `@return`, `@template`, `@var`, `@phpstan-assert*`) is load-bearing at level max and is never optional; `@phpstan-ignore` pragmas keep their parenthetical justification. Beyond those, keep only three things: contract prose a signature cannot carry (a null-meaning, a side effect, what a `mixed` return actually is — `ComponentManager::configureUsing()`); an invariant stated at its enforcement point (the `// Security:` sanitization blocks, whose downstream sinks embed the value raw and rely on the strip instead of per-sink escaping); and why a `catch` swallows, because an empty or bare catch is the one shape a reader reliably "fixes" (`HasActions`' `catch (Cancel)`). Even that yields to the trail: `StaticInstancePass`' `catch (Throwable)` carried such a comment until [support-bundle.md](docs/progress/support/support-bundle.md) explained the same swallow with a better example, at which point the comment was a duplicate. Remove rationale, divergence narration, restatement of the code below it, and historical notes — **`docs/progress/` is the system of record for reasoning, so a comment repeating it is a duplicate**, and a trail sentence that cites "the docblock" dangles the moment it goes. Provenance is not a defence: a comment Filament or Laravel also carries gets judged on the same terms, because comment style is idiom — translated like Blade → Twig — not API. The one hard rule when removing: **never delete reasoning that has no home in the trail** — write it there first, then delete.
- **Never pad a call with default values to reach a later parameter — name it.** `generateIconHtml(icon, null, null, iconSize)` becomes `generateIconHtml(icon, size: iconSize)`, `ErrorHandler::register(null, false)` becomes `ErrorHandler::register(replace: false)`. Applies to PHP and Twig alike (Twig takes `name: value` in a call). The padding is unreadable at the call site and silently wrong the moment the callee inserts a parameter, which a named argument survives. This is about *padding*: passing every parameter positionally with a real value each is fine (`generateIconHtml(icon, alias, attributes.all, size)`), and so is a leading positional run before the named one. A required parameter is never padding, even when the value is `[]` — check the signature before assuming.
- Prefer the idiomatic construct over manual mechanics, and actively hunt for one whenever code reads noisy or repetitive — the language/library usually ships a purpose-built syntax (e.g. Twig hash spread `...(x ?: {})` replaced `|merge(x ? x.toArray() : {})` chains; StimulusBundle's Twig helpers replaced hand-concatenated `data-*` attribute strings). Verify the candidate against the installed vendor source before relying on it.
